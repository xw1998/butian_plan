# 补天计划（Butian Plan）

**简体中文** | [English](README.en.md)

> **实践是检验真理的唯一标准**

AI 已经能回答很多问题，但长期合作还需要更多：记住你的要求，接续中断的任务，复用做对的方法，在出错后修正经验，并把复杂工作推进到可以验收的结果。

**补天计划就是为这些能力准备的增强层。** 将它接入你正在使用的 AI 应用，宿主 AI 便可以通过 MCP 调用补天的任务、记忆、上下文、证据和协作工具，把一次次对话连接成持续的工作过程。你继续使用熟悉的 AI，由补天保存工作进度和实践积累，无需额外部署 Ollama 或本地模型。

## 接入补天，你的 AI 能增强什么？

- **更能记住你：减少重复交代。** 将你的要求、纠正、项目背景和已确认结论保存为可检索的长期记忆，在后续任务中按需带回上下文。持续合作时，已经说清楚的事情有据可查。
- **更能接着干：长任务不轻易断线。** 保存当前目标、完成进度、证据、未决问题和下一步动作。会话压缩、任务交接或服务重启后，AI 可以据此恢复工作，减少重新梳理的成本。
- **更会做同类事：把成功方法留下来。** 将实际执行的方法、适用环境和结果沉淀为经验。再次遇到相似任务时，优先参考经过验证的步骤，减少重复查找和试错。
- **更能吸取教训：错误有机会变成改进。** 记录失败条件与用户反证，让冲突经验进入争议、修订和重新验证流程。旧方法不再适用时，可以更新版本，而不是一直沿用。
- **更善于处理复杂工作：从一个助手扩展到岗位协作。** 由主 Agent 对接用户，组织研究、实现、测试和审核；结合可用的子 Agent 执行接口，分发任务、收取交接、审核返工并汇总交付。
- **更有积累空间：从经历中提出下一条值得验证的线索。** “做梦”机制组织已有材料，由宿主 AI 提炼关联、矛盾与候选假设，再安排验证。经过验证的方法可以继续投入后续实践。

这些增强通过外部记忆、工具和工作流程发挥作用，依赖宿主 AI 在任务中实际调用。补天让使用过程中产生的经验持续可用；它不直接修改底层模型参数。

## 哪些工作最适合用补天？

**长期项目开发：** 今天完成模块实现，下次从未完成事项继续；某个工具版本踩过的坑，可以连同环境与验证步骤一起留给后续任务。

**反复处理同类业务：** 报表整理、资料研究、故障排查等工作中，把已经验证的做法逐步积累为可复用的方法，遇到例外再修订。

**需要分工与审核的复杂任务：** 让研究、实现、测试、审查各有职责，主 Agent 负责把分散结果组织成有证据、可验收的交付。

## 它怎样工作？

一个主 Agent 与你直接对话，负责理解需求、拆解任务、分发工作、组织审核并交付结果；不同岗位的子 Agent 承担研究、实现、测试、审查和复盘。简单任务也可以只用一个数字人，持续使用自己的独立记忆。

```text
用户
  ↕
派活者 / 主 Agent
  ├─ 研究子 Agent
  ├─ 实现子 Agent
  ├─ 测试子 Agent
  └─ 审核子 Agent
```

研究论文：人的实践经验形成过程的计算建模。

## 功能与机制详解

以下按当前源码中的业务模块说明能力。宿主 AI 负责理解、推理与生成，补天负责持久化状态、工具准入、执行协调和可核验证据；某项能力是否可实际执行，还取决于宿主接口、Provider 能力与当前授权。

### 1. 数字人身份、岗位与解题策略

每个成员具有独立 ID、名称、人格说明、岗位职责、Provider、模型及默认策略。初始化导入十名数字人的公开配置和方法知识，重复启动保持幂等，已有身份修改与用户记忆不会被初始资产覆盖。成员身份既用于显示，也参与任务归属、记忆访问、工具所有权和证据访问检查。

策略目录包含经验复用、模型建构、证据审查、实验迭代、设计综合、风险先行、用户情境和反方审计八种解题顺序。可按任务特征推荐或组合策略，也可由派活者覆盖成员默认策略。任务保存策略版本、阶段、覆盖理由与决策者，执行过程记录实际阶段。策略影响探索顺序，不能绕过验收、证据或授权；当前没有把某种策略宣传为已被统计证明更优。

### 2. 问题定义、澄清与纠正后的继续执行

任务可保存结构化问题定义：目标、约束与验收等内容随修订更新。需要用户回答时生成问题记录，使任务进入等待用户状态；回答与任务恢复有关联。用户改变条件后，系统核对问题修订、任务版本和已有执行绑定，避免旧目标下的结果直接覆盖新需求。

宿主导出的执行包绑定成员身份、任务与问题版本、上下文和显式方法引用。方法内容与验证信息形成快照，提交时重新核验；被归档、争议或替换的方法不能继续冒充原验证方法。任务恢复需要重新确认当前执行资格，旧会话存在不代表旧任务仍有效。

### 3. 单人工作、团队分工与审核闭环

单人模式由选定数字人处理目标；团队模式由派活者组织计划和子任务、分配执行成员、收取结构化交接并汇总。支持宿主驱动团队流程及可选 Provider 执行。成员可讨论问题、提交回答和方法，再通过验证记录同行学习结果。

任务状态机包含 todo、ready、claimed、running、review、done，以及 blocked、failed、waiting_user、cancelling、cancelled、provider_lost 和 unknown 等异常或等待状态。状态变化检查允许的迁移与修订，交付进入审核后才能批准完成；审核可要求返工，返工有次数边界。工具结果、子 Agent 文本或回显成功本身不构成验收通过。

### 4. 上下文分层、结构化交接与重启恢复

上下文装配按当前指令、任务、近期事件、相关记忆和历史索引分层分配预算，并报告裁剪情况。显式方法引用也受预算约束。当前约束、未决问题、用户纠正和下一步动作需要进入持久任务状态，不能只依赖聊天窗口。

快照保存事件范围、父快照与校验信息，追加事件日志提供恢复线索。交接包携带任务版本、状态、环境、证据、未完成事项与下一步动作。重启和恢复会区分已完成、在途及结果未知的执行；不能确认的副作用标记 unknown，避免直接当作成功或盲目重放。

### 5. 独立记忆、实践反馈与召回审计

每个数字人使用隔离的记忆空间，保存方法、经验、教训及其来源、环境、证据、适用条件和失效条件。召回结合查询与环境，提供后续决策参考；软件版本无法确认时标记 unknown，不能自动把不同环境的行为合并成一条确定规律。

实践结果以独立观察标识记录成功、失败或未知；重复观察受到去重与独立性约束。成功与失败更新经验和教训权重，重复收益采用 log1p 饱和方式，防止仅靠重复次数无限抬高可信度。召回结果另记录哪些记忆被使用、哪些有用或有害、是否漏召回及证据，便于追踪记忆是否真正帮助了任务。

用户异议可形成反证线索。系统保留争议与后续核查记录；需要核对输入、版本、配置、复现结果和替代解释，不能把尚未核实的反对意见直接等同证伪，也不能把旧经验一直作为事实使用。

### 6. 退化评估、降温复温、版本链与技能演化

记忆有热、温、冷和归档生命周期。维护考虑时间、验证情况、连续失败、矛盾、依赖漂移及环境变化；降温后仍保留历史，后续命中可作为待复核参考。复温需要新的实践结果和证据，不能只恢复旧分值。改进方法形成版本链，保留修改原因与前后关系。

记忆合成可引用多个组成记忆，并显式保存组合收益、冗余与冲突因素。领域技能保存阶段、边际变化、矛盾、新环境、独立成功、组合成功和回归证据等记录。验证批次跟踪样本量、通过与失败数及证据。这里的演化是运行期知识和方法管理，不代表更新神经网络参数。

### 7. 做梦、蒸馏、抽象与后续验证

做梦以已有片段为输入，受新增材料、最低片段数、最短间隔、并发锁、操作预算与成本约束。候选材料按权重、证据与近期验证等因素组织；维护可生成待处理任务，由宿主 AI 完成内容推理。后台调度不会自行拥有未配置的模型能力。

流程支持运行候选生成、蒸馏摘要、记录合并项与冲突、抽象模式、声明适用与失败条件、提出假设、安排验证和登记结果。梦境内容默认是候选，不能直接升级为可靠经验。验证后的候选仍需在后续真实任务中使用并积累独立观察，才进入相应经验生命周期；反例会触发争议和修订。

### 8. 外部来源学习与可追溯提取

来源登记记录定位、标题、内容 SHA-256、抓取时间和元数据；显式公开 URL 抓取保存正文快照并校验哈希，支持分段读取。学习队列使用领取、租约及续租记录组织处理，保留运行状态和失败。网络入口检查地址类型、重定向与大小限制，但现有检查不等价于完整网络隔离。

来源主张保存条件、限制、预测与反证条件。提取任务绑定原来源，审核发布核验来源身份和引文，防止伪造引用或替换来源后入库。主张可以转为先验，再准备实践假设；外部文本和初始方法卡均属于待验证知识，不因被抓取或审核排版就成为已实践经验。

### 9. 假设、探索预算与证据化观察

假设记录来源先验、论据、条件、预测与可证伪条件。验证动作声明成本、风险与预期信息增益，经过明确授权再启动；创建动作或预算充足均不自动授予工具权限。全局或成员预算限制时间窗内动作数、声明成本和风险，已开始但失败或结果未知的尝试仍计入消耗。

观察使用独立标识，支持与拒绝结论绑定仍有效、调用者可访问的证据。来源变化时重新核查，避免用失效来源完成验证。Beta 更新、信息增益与 Thompson Sampling 有数学模块和研究控制；不能把它们直接描述为所有生产 confidence 的自动后验，更不能称为完整 Bayesian RL。

### 10. 证据登记、访问控制与有效性复核

文件证据登记路径、所有者、内容指纹与可选过期时间，并支持向成员授予或撤回访问。审核、假设观察、工具验证和工作流准入会检查适用的证据资格。路径相同而内容变化、证据过期或权限撤回，都可能使过去的证明失效。

证据台账让结论可追溯，但不能替代业务判断：文件存在不等于结果正确，单个任务的自报成功也不等于独立验证。当前调用身份和任务归属参与访问控制，历史凭证不能自动继承到新任务或新版本。

### 11. 自有工具资产、经济准入与真实执行

工具有所有者、用途、源码版本、manifest、输入输出契约和哈希。提案记录成本与预期收益，验证、经济准入及状态共同决定能否使用；初始工具保持 draft，不因随包分发就变成稳定工具。版本变化需要重新检查相应资格。

执行前检查成员、任务、版本、源码与契约、验证状态、熔断器、宿主授权和预算；执行记录保存输入输出、耗时、状态与审计信息。支持查询在途执行、取消、重放审计和故障恢复。取消或超时必须以真实后端结果为准，停止无法确认时返回 unknown。工作目录容量是启动前及执行后的应用层计量，不应宣传为运行中 OS 硬上限；OS 隔离能力以执行后端实际声明为准。

### 12. 工具共享、试用、故障修复与升级工单

所有者可向指定成员共享工具，接收者接受后进行试用并记录证据；共享不等于把所有者的宿主授权转授给接收者。工具问题支持报告、分诊、请求及补充信息、关联重复问题、提交修复版本、原报告者确认和安全问题独立审核。

到期问题可形成升级工单，由有资格的成员领取、处理或退回，维护保留关联与去重记录。熔断器用于阻止继续使用风险版本，恢复需要相应条件。归档会检查在途执行及工作流引用；恢复资产后仍须满足当前准入，不能绕过旧故障或失效证据。

### 13. 工具迁移与版本化工作流

工具包导出源码、连续版本和公开契约白名单，对源码、manifest 与包体做哈希校验。导入检查格式、大小、版本和声明信息，工具进入 draft，需要重新验证与授权；私有记忆、运行数据库和宿主授权不随包迁移。许可和扫描状态由调用方声明，不等于系统实际完成外部安全扫描。

工作流固定每步工具版本、源码与契约哈希，并声明总超时、输出预算、权限与失败条件。每步复用工具准入和审计。至少两个不同任务、证据内容不重合的真实组合验证才满足激活要求；单工具通过不能替代组合验证。依赖或证据失效会要求复核；中断恢复标记 unknown，不重放副作用；不能获得真实中间输出的多步 dry-run 不冒充预演通过。

### 14. Provider、宿主执行与跨应用接入

通用 Provider 层支持能力协商，并提供本地进程、HTTP、MCP 与人工交接等适配路径。开始、消费、取消、会话归属和任务修订需要保持绑定。宿主 MCP 模式直接使用当前 AI 的推理与工具，不需要额外部署模型；只有补天主动调用独立执行者时才需要相应 Provider 配置。

能力缺失明确返回 unsupported 或 unknown。Provider 回显只验证传输与状态链；实际模型回答、浏览器交互、Office 渲染、设备操作和外部服务访问必须由具备能力的宿主或后端执行，并各自提供证据。成员历史迁移入口当前明确禁用，不将初始资产导入描述成用户历史迁移。

### 15. 本地服务、事务审计与备份恢复

CLI、stdio MCP 和本地 HTTP API 共用运行时，Web 提供总览、任务、验证、记忆、进化、成员视图。SQLite 保存任务、事件、运行台账和成员相关索引，独立记忆库保存成员知识。关键入口使用写锁、写预约或保存点保护业务与审计；跨独立数据库、文件系统和服务事件并不存在通用原子事务，恢复记录用于处理部分完成。

备份提供创建、验证与恢复入口，恢复到新目标以避免覆盖当前运行库。备份校验及路径、链接和重解析点检查用于防止越界和损坏；具体平台能力仍需满足运行环境。运行库与凭据属于本地用户状态，公开初始交换库只携带公开配置、知识和工具。

### 16. 初始知识、研究材料与可复核边界

随包十名成员各有方法卡、工具指南和专业工具，初始化导入为 candidate/零置信知识与 draft 工具。实际专业范围和数量以资产目录为准，来源见 `butian/assets/catalog.json`，工具契约见 `butian/assets/professional_tools.json`；后续成功实践才产生经验。

论文和实验脚本用于说明机制、成本和局限。确定性宿主控制、数学模拟、生产接口回放、非盲 Agent 试跑与真实模型确认性实验分别报告，不能混为模型能力证明。研究模块不是产品使用前提；模块存在、专项通过和产品全场景验收也分别表述。

### 17. 一次任务如何形成可复用经验

完整链路从具体问题开始，而不是从保存一句总结开始。宿主先记录目标、当前环境、约束和验收条件，再召回可能适用的方法。召回仅提供候选；宿主仍须比较任务实体、软件版本、前置条件和失效条件，存在冲突时重新取证，来源不可用时保留 unknown。采用方法后执行真实行动，保存首次结果、工具输出和可复核证据，最后把成功、失败或未知写回，而不是事后改写首次答案。

生产 `record_practice_outcome` 要求非空的独立观察标识；成功必须携带证据引用，服务还会验证归属与内容指纹。独立键、证据引用及内容摘要共同限制重复计数，换一个文件名或观察编号不等于新的独立实践。候选达到至少两次通过接口去重的成功、没有失败且原状态为 candidate 或 pending_validation 时，才由该接口升级为 warm。成熟经验失败进入 disputed；未知不增加成功或失败计数。这是程序准入门槛，不是统计独立或普遍正确的证明，直接调用底层写入也不能冒充经历了这套验证。

修订保留父版本、原因、环境、来源和证据。版本变化不允许仅凭旧规则宣称新环境已验证；遇到反例也不能删除历史来恢复可信。生产 confidence 的有界调整、权重更新与可选 Beta 数学模块是不同机制；warm 表示满足指定接口门槛，不表示“已证明”。宿主必须实际提交反馈，系统不会仅凭聊天内容自动知道行动是否成功。

### 18. 宿主接入的职责与失败处理

在宿主驱动方式中，现有 AI 应用提供模型、当前会话和工具能力，补天提供成员身份、任务状态、候选上下文、执行包、证据和反馈接口。一次执行需要读取当前任务及问题修订，领取或恢复合法执行资格，装配上下文，执行并返回真实结果，再提交交接和审核。用户纠正改变目标时，应按新修订重新接续；旧执行包、旧工具验证或旧会话不能自动获得新任务资格。

在主动 Provider 方式中，先核对能力协商及授权，再启动独立执行者；结果消费与取消绑定同一任务、修订和会话。传输成功只说明消息到达，不说明业务验收通过。超时、后端失联或停止未确认时保留 unknown/provider_lost 等实际状态，不伪造 cancelled 或 done。恢复前检查已提交记录和未决行动，具有副作用的调用不能无条件重放。

单人任务与团队子任务使用同样的证据边界。派活者应从交接包中检查任务版本、结果、来源、未完成事项及下一步，再决定审核、返工、阻塞或等待用户；不能把成员的自报成功直接汇总成结论。浏览器、Office 排版和设备操作仍需对应宿主能力，不因配置了一个数字人就自动具备。

### 19. 来源、假设和工具的边界如何衔接

外部材料首先作为带定位与哈希的来源快照进入学习链路；从中提取的主张须保留引文、条件、限制和反证条件。做梦将既有材料组织成摘要、抽象和候选假设，内容推理由宿主完成。提出假设、排入验证队列、取得预算、获得执行授权、启动动作和登记观察是不同步骤，任一步完成都不能代替后续步骤。supported 只支持当前验证范围内的候选，后续真实实践仍须按经验接口累计。

工具也不是源码一导入就能执行。所有权、版本、输入输出契约、源码哈希、验证资格、经济准入、熔断状态、当前任务、预算和宿主授权共同决定准入；工作流还固定各步依赖版本并要求真实组合验证。包迁移只搬运允许公开的资产与契约，不搬运私有记忆、运行库、凭据或宿主授权。材料内容变更、证据过期、访问撤销或依赖失效均需重新核查，过去一次通过不能永久替代当前资格。

### 20. 部署、数据边界与研究结论

初始化用于建立本地运行目录、成员和公开初始资产；CLI、stdio MCP 和本地 Web/API 是同一运行时的不同入口。需要宿主调用时使用 MCP，需要主动执行独立 Agent 时再配置 Provider。运行数据库、证据原件、执行工作目录和授权信息由部署者在本机管理，备份恢复到新目标并先做完整性检查。该设计不等于操作系统沙箱或面向公网的完整隔离，真实隔离能力以部署与后端声明为准。

项目说明以本 README 正文为完整公开入口；内部需求过程、开发验收记录和本机日志不作为公开使用手册，也不通过放宽白名单来修复链接。论文作为独立研究材料，报告确定性规则复用、接口控制、数学控制和做梦回放的各自结论。源读取减少不等于总操作更少或端到端更快，合成任务没有语言模型调用也不代表模型能力提高；正常关闭重启不等于任意断电恢复。运行期经验库改变上下文与方法选择，不自动改变模型参数。


## 核心能力

- 单人模式：用户直接与一个数字人协作，适合简单任务。
- 团队模式：派活者负责对接用户，子 Agent 按岗位分工执行任务。
- 数字人资产：支持配置名称、人格、职级、岗位、职责、模型和工具权限。
- 独立记忆：每个数字人拥有隔离的长期记忆、经验和教训，并支持热、温、冷、归档生命周期。
- 任务闭环：支持拆解、分发、执行、审核、返工、阻塞和取消。
- 通用 Agent Provider：通过能力协商接口接入不同 Agent 运行时、模型 API、本地模型、MCP 或人工执行，不为任何单一产品定制核心生命周期。
- 开箱即用的成员配置：初始化十名数字人，带有按专业整理的初始知识与工具，各自积累独立记忆，可按工作需要调整岗位与职责。

## 单人模式与团队模式

单人模式适合目标清晰、无需交叉验证的任务。选定一个数字人后，该数字人直接理解和执行任务，并使用自己的独立记忆。

团队模式适合复杂任务。派活者是用户的主要对话人，子 Agent 只以自己的身份执行分配到的任务。派活者必须汇总可复核证据，不能把尚未验证的子 Agent 输出直接当成最终事实。

可以按任务复杂度选择协作方式，任务与记忆持续保留，便于追踪进展和接续工作。

网页工作台的“提交目标”是一张表：顶部的「单人执行 / 团队分工」可以随时切换，**已填的目标与验收条件不会丢**。切到团队时，执行成员是逐个勾选的，每个人后面就跟着自己的子任务输入框——分工按“成员→子任务”直接配对，不会再出现“子任务行数必须等于成员人数”这类对不上的错误。执行方式（当前 AI 应用/人工交付，或已配置 Provider）两种模式共用：没有配置 Provider 也能提交团队目标并派活，任务会停在等待外部执行。

## 防止上下文黑洞

补天计划不把 AI 对话窗口当作唯一事实来源。当前任务状态、用户纠正、未决问题、证据、任务交接和下一步动作都会写入结构化状态包与追加事件日志。

长会话接近上下文窗口时，系统按“当前指令、当前任务、近期事件、相关记忆、历史索引”分层压缩。低优先级历史可以裁剪，但当前用户约束、任务状态、最近纠正、未决问题和下一步动作不能丢失。压缩快照保留父快照、事件范围和校验信息，重启后可以恢复或从事件日志重建。

子 Agent 交给派活者的是带任务版本、状态、证据、环境、未完成事项和下一步动作的结构化交接包，不是无法追溯的一段文本。已证伪、环境不匹配和低置信推测不会无提示地进入确定性上下文。

## 经验与教训：可积累的资产

补天计划中的经验和教训不是普通聊天记录，而是可以持续改善 Agent 的重要工程资产。

它们可以用来：

- 调整数字人的提示词和工作方法。
- 选择更合适的模型、工具和子 Agent。
- 改进任务拆解、审核和验证策略。
- 在相同环境下复用已经验证过的解决方案。
- 识别已知失败条件，避免重复踩坑。

使用工具或外部软件时，经验和教训必须绑定环境信息，包括软件名称、版本号或 commit、模型版本、操作系统、依赖版本、关键配置、复现步骤、证据路径、验证时间、适用范围和失效条件。版本无法确认时必须标记为 `unknown`，不能把不同版本下的行为自动合并。

经验和教训会从实践结果中自动吸收，不把人工确认作为学习前置条件。做事成功就记录方法和环境作为经验；做事失败就记录失败方法和环境作为教训；相同方法再次成功或失败时，使用 `log1p` 饱和曲线更新权重，重复次数越多，新增一次结果的收益越低。客户提出异议时，异议会自动记录为待评估的反证事件。系统需要核对版本、输入、配置、复现结果和替代解释后，才能判定证伪成立；证据不足时只能标记争议或临时降权，不能直接推翻原经验。没有充分证据的内容仍必须标注低置信度或未验证状态。

## 做梦机制：让 Agent 从实践中发现新线索

做梦是独立记忆系统的后台维护机制，主要由经验和教训积累到足够数量与强度时触发，而不是单纯按固定时间触发。它从已经记录的经历、经验和教训中寻找：

- 新的记忆关联。
- 尚未解决的知识缺口。
- 互相矛盾的经验。
- 可以在未来任务中验证的候选假设。

做梦产物默认属于推测内容，不能直接当作事实。只有经过真实实践、人工确认或可靠证据验证后，才可以转化为高可信经验或教训。

做梦优先从权重最高、证据最充分、最近验证过的记忆事件开始；越久远、越少验证或已证伪的事件，进入梦境的概率越低。原有闸门继续保留：积累足够的经验和教训、满足最短间隔、新增片段达到阈值、取得做梦锁，并受操作数和成本上限限制。只有同时满足条件才运行。这样既能让模型及时拓展想象，也能避免无意义地反复调用模型。

经验、教训和做梦机制共同构成补天计划的长期资产。记忆还会经历热、温、冷和归档生命周期：长期不用的经验会进入冷数据，后续任务命中时以“需要重新验证”的历史参考方式复温；同一经验在新实践中还会形成 v1、v2、v3 的修订链，把更好的步骤、工具、前置条件和验证方式逐步合并进去，重新成功后才逐步恢复权重。这就是“温故而知新”：经验会在实践中变得更好，而不是简单恢复旧权重。内置成员带有独立的初始方法知识；这些知识标为未实践候选，经验、教训和工具验证数据只通过本系统实际运行逐步积累。所有 Agent 工具均通过通用 Provider 能力协议接入，不包含固定产品的插件界面、会话生命周期或特殊功能。它们可以帮助调整 AI，使 Agent 在可追溯、可验证的前提下逐步改进，而不是把“自进化”实现成不可解释的自动改写。

## 轻量部署，接入现有 AI

使用 **Python 3.11+** 与内置 SQLite 保存本地状态：

- 标准库已经覆盖 SQLite、异步任务、命令行、HTTP 和数据处理的基础需求。
- `sqlite3`、`asyncio`、`pathlib`、`json` 等可以减少外部依赖。
- 适合先把记忆、任务状态机和 Provider 抽象跑通。
- OpenAI 兼容接口、Ollama、MCP 和本地脚本都有成熟接入方式。

核心运行时仅使用 Python 标准库，提供本地 Web 工作台、CLI 和 stdio MCP 接口。宿主应用支持 MCP 时即可接入；需要主动调度独立子 Agent 时，再按需配置 Provider。

核心接口保持平台无关；外部 Agent 工具只实现通用 Provider 能力协议，能力不支持时明确返回 `unsupported` 或 `unknown`。

## 快速开始

### 环境要求

- Python 3.11+（仅使用标准库，无第三方依赖）
- SQLite（Python 内置）

### 安装与运行

```bash
# 1) 初始化运行时（默认目录 ~/.butian，可用 BUTIAN_HOME 指定）
python -m butian.cli init

# 2) 添加一个数字人成员
python -m butian.cli member add m1 Alice

# 内置十名数字人由初始化流程创建，导入各自的初始方法知识与工具。
# 历史迁移不在当前范围内，migrate 入口返回明确拒绝。

# 3) 启动团队工作台（本地 HTTP API + Web 控制台）
python -m butian.cli serve --host 127.0.0.1 --port 8765
#   浏览器打开 http://127.0.0.1:8765

# 4) 以 MCP 服务方式接入（JSON-RPC over stdin/stdout）
python -m butian.cli mcp
```

### 本机工作台入口与升级

固定入口为 **http://127.0.0.1:8765/**。使用上述 `--host 127.0.0.1 --port 8765` 命令启动后，从姓名和角色下拉框选择数字人，点击“进入工作台”，**无需设置或输入令牌**。成员选择决定当前工作身份与数据范围。

升级流程：先结束运行中的任务，再在原后台终端按 `Ctrl+C` 关闭旧服务；随后更新源码、执行 `python -m pip install -e .`，用同一条命令重新启动到 8765。停止任务不会自动停止后台；仅更新文件或刷新浏览器也不会重新加载 Python 服务。端口占用时先关闭原服务，不必改用其他端口。

若仍看到令牌框，核对启动终端的版本和监听地址，再刷新页面。服务响应包含 `X-Butian-Version` 版本头，并禁止缓存控制台资源。绑定 `0.0.0.0` 或其他非回环地址属于远程部署，仍要求成员认证；本机使用请绑定 `127.0.0.1`。AI 应用的 MCP 连接也需重新连接才能加载更新。

### 接入 AI 应用

宿主应用支持 stdio MCP 时，配置命令 `python`、参数 `["-m", "butian.cli", "mcp"]`，工作目录设为仓库目录，环境变量 `BUTIAN_HOME` 指向你的数据目录。Python 应使用已安装本项目的解释器。不同客户端配置字段不同，请按宿主应用的 MCP 配置格式填写。

宿主 AI 自己负责理解目标和生成结果，调用补天的任务、上下文、证据、审核与记忆工具；这条路径无需 providers.json、模型 API Key 或 Ollama。补天主动启动独立子 Agent 时，才配置可选 Provider。没有 MCP/API/进程接口的应用只能人工交接。

总览、任务、验证、记忆、进化、成员六个工作区。「成员」视图展示成员身份与配置；随包初始资产会幂等导入；用户运行库不作为公共资产。其中「进化」是数字人自由进化的操作台：技能阶段、记忆合成、记忆维护（退化评估/降温/复温/版本链）、梦境自省（运行/蒸馏/抽象/提出假设/安排验证/记录结果）、验证批次、以及假设与验证队列。

- 宋析：CSV 类型与结构审查；林知：文献记录规范化及 DOI 去重；文澜：PDF 页码、尺寸与文字层检查；叶青：HTML 静态结构审查。
- 每位数字人另有独立的基础复核工具，支持统计、独立不确定度分量合成、检查清单与文本指纹。
- 浏览器、Office 渲染和专有在线服务依赖宿主提供能力；初始资产不携带凭据，不将静态检查冒充实际操作验收。PDF 检查可选依赖 `pdfplumber`，图像分析可选依赖 OpenCV。

这些资产是 **未实践的方法知识**，不是已验证经验，也不是模型参数训练。知识保持 candidate、置信度为零，工具保持 draft；调用仍经过现有授权与执行后端。初始卡片不会自动作为新实践触发做梦。后续真实任务的结果才形成实践证据。

仓库随附 `butian/assets/initial_knowledge.sqlite3`，只包含公开数字人配置、知识和工具源码，不含用户运行数据库。可在新路径重建交换库，或创建可直接启动的干净运行库：

```bash
python -m butian.assets.build /absolute/new/initial.sqlite3
python -m butian.assets.export /absolute/new/runtime
```

目标必须不存在；命令拒绝覆盖已有目录或数据库。正常服务启动会从随包 JSON 和工具资源导入资产，重复启动不会重复登记。交换库不含运行期身份认证信息；运行库需在本机创建。

### MCP 参数发现与失败恢复

- 用 `butian_tools_catalog` 分页查看工具摘要（`offset`、`limit`，每页最多 30 项，可用 `prefix` 筛选名称），再用 `butian_tool_schema(name)` 获取单工具完整参数，避免一次输出全部 schema 被截断。
- 缺参数或顶层参数类型错误返回 `invalid_tool_arguments`，MCP 工具错误正文 `details.issues` 列出字段与原因，不回显传入值或凭据。业务失败保留原错误码；已认证且可见的任务才附带当前状态、revision、执行模式、缺失条件及恢复动作。
- 普通任务创建只登记 todo。手动执行流程为 `task_transition(todo→ready)` → `task_claim` → 用新 revision 推进 `claimed→running` → 执行并登记真实证据 → `task_handoff` → 按审核规则进入/处理 review。提示中的动作片段仍需补认证信息与幂等操作键，不能当作完整请求直接重放。
- 标准 AI 宿主执行应通过 `butian_goal_submit` 建立宿主任务及验收条件，再 `butian_execution_export`；该入口对符合条件的宿主任务可自动推进至 running。`external_execution_required` 指执行模式不匹配，不意味着简单推进 running 即可解决。不要为消除错误擅自重建已有任务。
- 当前成员 MCP 入口的实验接口受管理员边界限制，不能靠换成员或填写任意 token 解锁。单工具 schema 会明确标示此限制；请由获授权的操作者走受支持的实验入口，本次没有开放管理员能力。
- 文件登记与 SHA256 核验只证明证据及完整性；不证明实验设计、结论或任务审核已经通过。`evidence_ref` 应填写已登记的证据 ID，不是路径。审核仍需真实交付与授权审核者判断。

### 协作就绪预检（开发中）

开始委派前调用 `butian_collaboration_preflight`，提供当前已认证的 `actor_member_id`，可选目标 `member_id` 和可见的 `task_id`。直连 MCP 仍须提供对应 token；受信本地桥可内部注入，不能把本机网页免令牌规则套用到任意 MCP。

预检只读检查成员边界、记忆可读性、Provider 配置以及已有任务的认领/审核条件。跨成员未授权时立即返回 `member_memory_access_denied`，不检查或泄露目标成员的记忆、Provider 配置。配置检查通过不等于模型可实际调用：`execution_verified=false` 明确表示尚未执行。证据登记、哈希核验和独立审核未经实际执行时保持 `unchecked`，不会把健康检查当作协作验收。

`butian_status` 区分服务存活与协作就绪，并给出预检入口。标准 MCP `tools/list` 每页返回最多 8 个完整 schema，首屏优先展示状态、目录、schema、预检与目标接口；宿主应按 `nextCursor` 继续翻页。若宿主自动聚合所有页，仍可能展示全部工具；需要简短查询时使用 `butian_tools_catalog`。补天自带 MCP Provider 已支持分页消费。

当前认证模型要求成员操作的 actor 与 member 相同，没有跨成员委派授权接口。真实数字人执行需要其自身已认证连接与可用 Provider。任务审核还受会话调度员/执行者身份限制；第三位成员并不自动获得审核权。以上预检不会新增授权、自动换身份或伪造独立审核。

`butian_collaboration_start` 是最小高层执行入口：先执行只读预检，问题仍需澄清或 Provider/权限不满足时不创建任务；条件满足才创建并启动当前已认证成员的 Provider，并返回下一步消费入口。它不模拟分析结果，也不把启动成功当成独立审核完成。当前隔离验收库若成员没有 Provider，预检会明确返回 `provider_unavailable`。

## AI 使用入口（0.1.8 起）

面向 AI 宿主收敛为三步，避免每次调用重复拼身份、会话与子任务：

1. `butian_connect` 绑定当前成员一次。本机默认不需要口令；存在多个成员时必须显式指定，服务端不猜。此后成员类工具自动继承身份。
2. `butian_mode` 读写单人/多人模式，**不需要 session_id**；切换只影响后续目标，运行中任务保留。
3. `butian_context` 一次返回当前成员、模式、可见任务（含 revision）与下一步合法动作，替代宿主自行追踪 session_id 与 revision。

`butian_goal_submit` 的 `mode` 可省略，默认取当前模式。团队模式省略 `subtasks` 时按成员职责生成确定性分工（`plan_source=deterministic_role_split`，明确标注未调用模型）；省略 `member_ids` 时把全部其他成员纳入分工并回显 `worker_selection=all_other_members`。**单人模式传 `member_ids` 会直接报 `member_ids_require_team_mode` 并给出切模式的动作，不再静默丢弃**。

`butian_context` 的 `next_actions` 按任务状态给，不是一律兜售“再建一个目标”：`todo→ready`、`ready→认领`、`claimed→running`、`running→review` 都直接给好 `task_id`、`expected_revision`、`target` 与 `operation_key`，复制即可执行；已有可推进任务时不再提示新建目标。派发者不会被建议代做其他成员的任务（只给 `butian_task_tree` 看进度），审核建议只给非本人任务。

工具第一页固定为“状态 / 连接 / 上下文 / 模式 / 提交目标 / 任务列表 / 目录 / schema”，其余工具按 `nextCursor` 翻页；`butian_tools_catalog` 支持 `query` 子串过滤（匹配名称与描述），无匹配时返回 `catalog_query_no_match` 并给出可用入口。`butian_task_claim` 的 `member_id` 默认取已连接成员，`butian_task_transition` 的 `operation_key` 缺省按 `task:revision:target` 派生，`actor_member_id` 与 `token` 也不再出现在这些工具的必填项里。

身份与口令仍写在工具的 schema 必填里（这些工具确实需要认证），但 `butian_connect` 之后由连接自动注入，**连一次就不必每次重传** `member_id`/`actor_member_id`/`token`；没连接时缺身份会直接得到“先 `butian_connect`”的下一步，而不是让人猜。只有 `butian_hypothesis_action_grant`、`butian_tool_security_review`、`butian_tool_repair_confirm`、`butian_dispatcher_set`、`butian_host_authorization_*` 这些 **member_id 指向别人或独立角色**的工具不会被注入——默认成自己会把“授权、独立复核”变成自我授权。可选参数传 `null` 视为未提供，不会因模板留空被判类型错。

同一执行者重复提交同名目标不会失败，但会在返回里带 `duplicate_of` 与 `duplicate_note`（指出已有任务的 `task_id` 与状态）——静默产生两份互相看不见的工作才是真问题；刻意并行时改一句目标描述即可。

执行结果没有被执行器确认时（`status` 为 `unknown` / `provider_lost` / `failed`），返回里带 `trustworthy: false`、`diagnosis`（`reason` 与“为什么不能当完成”）和 `next_actions`（先 `butian_context` 看上下文与合法下一步，再 `butian_provider_start` 用新会话重发）。这类状态既不能写进审核，也不该手工改状态绕过确认。

本机回环工作台在 `/api/goals/host-submit` 这类走工具层的接口上同样不需要口令（服务端为当前请求绑定本机代表），**但显式传了口令就按口令校验**：错口令仍然失败，本机免口令不等于“错口令也算对”。

`butian_goal_submit` 接受把问题模型字段直接写在顶层（如 `acceptance_criteria`），与写在 `problem` 里等价；同一字段两处取值不同会报 `problem_field_conflict`，**拼错或未知的参数会报 `unknown_argument` 并列出被接受的参数名**，不再静默忽略（以前顶层 `acceptance_criteria` 会被丢掉，目标莫名停在 `needs_clarification`）。

报错一律带“缺什么、下一步调用什么”：对象不存在（`knowledge_source_not_found`、`source_snapshot_not_found`、`memory_not_found`、`tool_version_not_found` 等）会给出能看见/建立该对象的工具；`butian_knowledge_source_add` 只登记哈希，读过正文前需先 `butian_knowledge_source_verify`（校验通过即落可读快照）或 `butian_knowledge_source_capture`；`butian_task_tree` 的 `payload` 直接返回解析后的对象，不再是二次编码字符串。

便利不改变边界：跨成员仍是 `member_memory_access_denied`；共享部署可设 `BUTIAN_MCP_TOKEN_REQUIRED=1` 恢复逐次口令；启动成功不代表执行成功，也不代表独立审核。

```bash
butian mcp                      # 本机 stdio，默认免口令
BUTIAN_MCP_TOKEN_REQUIRED=1 butian mcp   # 共享部署，恢复口令校验
```
