# 补天计划（Butian Plan）

**简体中文** | [English](README.en.md)

> **实践是检验真理的唯一标准**

AI 已经能回答很多问题，但长期合作还需要更多：记住你的要求，接续中断的任务，复用做对的方法，在出错后修正经验，并把复杂工作推进到可以验收的结果。

**补天计划就是为这些能力准备的增强层。** 将它接入你正在使用的 AI 应用，宿主 AI 便可以通过 MCP 调用补天的任务、记忆、上下文、证据和协作工具，把一次次对话连接成持续的工作过程。你继续使用熟悉的 AI，由补天保存工作进度和实践积累，无需额外部署 Ollama 或本地模型。

## 接入补天，你的 AI 能增强什么？

- **更能记住你：减少重复交代。** 将你的要求、纠正、项目背景和已确认结论保存为可检索的长期记忆，在后续任务中按需带回上下文。持续合作时，已经说清楚的事情有据可查。
- **更能接着干：长任务不轻易断线。** 保存当前目标、完成进度、证据、未决问题和下一步动作。会话压缩、任务交接或服务重启后，AI 可以据此恢复工作，减少重新梳理的成本。
- **更会做同类事：把成功方法留下来。** 将实际执行的方法、适用环境和结果沉淀为经验。再次遇到相似任务时，优先参考经过验证的步骤，减少重复查找和试错。
- **更能吸取教训：错误有机会变成改进。** 记录失败条件与用户反证，让冲突经验进入争议、修订和重新验证流程。旧方法不再适用时，可以更新版本，而不是一直沿用。
- **更善于处理复杂工作：从一个助手扩展到岗位协作。** 由主 Agent 对接用户，组织研究、实现、测试和审核；结合可用的子 Agent 执行接口，分发任务、收取交接、审核返工并汇总交付。
- **更有积累空间：从经历中提出下一条值得验证的线索。** “做梦”机制组织已有材料，由宿主 AI 提炼关联、矛盾与候选假设，再安排验证。经过验证的方法可以继续投入后续实践。

这些增强通过外部记忆、工具和工作流程发挥作用，依赖宿主 AI 在任务中实际调用。补天让使用过程中产生的经验持续可用；它不直接修改底层模型参数。

## 哪些工作最适合用补天？

**长期项目开发：** 今天完成模块实现，下次从未完成事项继续；某个工具版本踩过的坑，可以连同环境与验证步骤一起留给后续任务。

**反复处理同类业务：** 报表整理、资料研究、故障排查等工作中，把已经验证的做法逐步积累为可复用的方法，遇到例外再修订。

**需要分工与审核的复杂任务：** 让研究、实现、测试、审查各有职责，主 Agent 负责把分散结果组织成有证据、可验收的交付。

## 它怎样工作？

一个主 Agent 与你直接对话，负责理解需求、拆解任务、分发工作、组织审核并交付结果；不同岗位的子 Agent 承担研究、实现、测试、审查和复盘。简单任务也可以只用一个数字人，持续使用自己的独立记忆。

```text
用户
  ↕
派活者 / 主 Agent
  ├─ 研究子 Agent
  ├─ 实现子 Agent
  ├─ 测试子 Agent
  └─ 审核子 Agent
```

## 核心能力

- 单人模式：用户直接与一个数字人协作，适合简单任务。
- 团队模式：派活者负责对接用户，子 Agent 按岗位分工执行任务。
- 数字人资产：支持配置名称、人格、职级、岗位、职责、模型和工具权限。
- 独立记忆：每个数字人拥有隔离的长期记忆、经验和教训，并支持热、温、冷、归档生命周期。
- 任务闭环：支持拆解、分发、执行、审核、返工、阻塞和取消。
- 通用 Agent Provider：通过能力协商接口接入不同 Agent 运行时、模型 API、本地模型、MCP 或人工执行，不为任何单一产品定制核心生命周期。
- 开箱即用的成员配置：初始化十名数字人，带有按专业整理的初始知识与工具，各自积累独立记忆，可按工作需要调整岗位与职责。

## 单人模式与团队模式

单人模式适合目标清晰、无需交叉验证的任务。选定一个数字人后，该数字人直接理解和执行任务，并使用自己的独立记忆。

团队模式适合复杂任务。派活者是用户的主要对话人，子 Agent 只以自己的身份执行分配到的任务。派活者必须汇总可复核证据，不能把尚未验证的子 Agent 输出直接当成最终事实。

可以按任务复杂度选择协作方式，任务与记忆持续保留，便于追踪进展和接续工作。

## 防止上下文黑洞

补天计划不把 AI 对话窗口当作唯一事实来源。当前任务状态、用户纠正、未决问题、证据、任务交接和下一步动作都会写入结构化状态包与追加事件日志。

长会话接近上下文窗口时，系统按“当前指令、当前任务、近期事件、相关记忆、历史索引”分层压缩。低优先级历史可以裁剪，但当前用户约束、任务状态、最近纠正、未决问题和下一步动作不能丢失。压缩快照保留父快照、事件范围和校验信息，重启后可以恢复或从事件日志重建。

子 Agent 交给派活者的是带任务版本、状态、证据、环境、未完成事项和下一步动作的结构化交接包，不是无法追溯的一段文本。已证伪、环境不匹配和低置信推测不会无提示地进入确定性上下文。

## 经验与教训：可积累的资产

补天计划中的经验和教训不是普通聊天记录，而是可以持续改善 Agent 的重要工程资产。

它们可以用来：

- 调整数字人的提示词和工作方法。
- 选择更合适的模型、工具和子 Agent。
- 改进任务拆解、审核和验证策略。
- 在相同环境下复用已经验证过的解决方案。
- 识别已知失败条件，避免重复踩坑。

使用工具或外部软件时，经验和教训必须绑定环境信息，包括软件名称、版本号或 commit、模型版本、操作系统、依赖版本、关键配置、复现步骤、证据路径、验证时间、适用范围和失效条件。版本无法确认时必须标记为 `unknown`，不能把不同版本下的行为自动合并。

经验和教训会从实践结果中自动吸收，不把人工确认作为学习前置条件。做事成功就记录方法和环境作为经验；做事失败就记录失败方法和环境作为教训；相同方法再次成功或失败时，使用 `log1p` 饱和曲线更新权重，重复次数越多，新增一次结果的收益越低。客户提出异议时，异议会自动记录为待评估的反证事件。系统需要核对版本、输入、配置、复现结果和替代解释后，才能判定证伪成立；证据不足时只能标记争议或临时降权，不能直接推翻原经验。没有充分证据的内容仍必须标注低置信度或未验证状态。

## 做梦机制：让 Agent 从实践中发现新线索

做梦是独立记忆系统的后台维护机制，主要由经验和教训积累到足够数量与强度时触发，而不是单纯按固定时间触发。它从已经记录的经历、经验和教训中寻找：

- 新的记忆关联。
- 尚未解决的知识缺口。
- 互相矛盾的经验。
- 可以在未来任务中验证的候选假设。

做梦产物默认属于推测内容，不能直接当作事实。只有经过真实实践、人工确认或可靠证据验证后，才可以转化为高可信经验或教训。

做梦优先从权重最高、证据最充分、最近验证过的记忆事件开始；越久远、越少验证或已证伪的事件，进入梦境的概率越低。原有闸门继续保留：积累足够的经验和教训、满足最短间隔、新增片段达到阈值、取得做梦锁，并受操作数和成本上限限制。只有同时满足条件才运行。这样既能让模型及时拓展想象，也能避免无意义地反复调用模型。

经验、教训和做梦机制共同构成补天计划的长期资产。记忆还会经历热、温、冷和归档生命周期：长期不用的经验会进入冷数据，后续任务命中时以“需要重新验证”的历史参考方式复温；同一经验在新实践中还会形成 v1、v2、v3 的修订链，把更好的步骤、工具、前置条件和验证方式逐步合并进去，重新成功后才逐步恢复权重。这就是“温故而知新”：经验会在实践中变得更好，而不是简单恢复旧权重。内置成员带有独立的初始方法知识；这些知识标为未实践候选，经验、教训和工具验证数据只通过本系统实际运行逐步积累。所有 Agent 工具均通过通用 Provider 能力协议接入，不包含固定产品的插件界面、会话生命周期或特殊功能。它们可以帮助调整 AI，使 Agent 在可追溯、可验证的前提下逐步改进，而不是把“自进化”实现成不可解释的自动改写。

## 轻量部署，接入现有 AI

使用 **Python 3.11+** 与内置 SQLite 保存本地状态：

- 标准库已经覆盖 SQLite、异步任务、命令行、HTTP 和数据处理的基础需求。
- `sqlite3`、`asyncio`、`pathlib`、`json` 等可以减少外部依赖。
- 适合先把记忆、任务状态机和 Provider 抽象跑通。
- OpenAI 兼容接口、Ollama、MCP 和本地脚本都有成熟接入方式。

核心运行时仅使用 Python 标准库，提供本地 Web 工作台、CLI 和 stdio MCP 接口。宿主应用支持 MCP 时即可接入；需要主动调度独立子 Agent 时，再按需配置 Provider。

核心接口保持平台无关；外部 Agent 工具只实现通用 Provider 能力协议，能力不支持时明确返回 `unsupported` 或 `unknown`。

## 快速开始

### 环境要求

- Python 3.11+（仅使用标准库，无第三方依赖）
- SQLite（Python 内置）

### 安装与运行

```bash
# 1) 初始化运行时（默认目录 ~/.butian，可用 BUTIAN_HOME 指定）
python -m butian.cli init

# 2) 添加一个数字人成员
python -m butian.cli member add m1 Alice

# 内置十名数字人由初始化流程创建，导入各自的初始方法知识与工具。
# 历史迁移不在当前范围内，migrate 入口返回明确拒绝。

# 3) 启动团队工作台（本地 HTTP API + Web 控制台）
python -m butian.cli serve --host 127.0.0.1 --port 8765
#   浏览器打开 http://127.0.0.1:8765

# 4) 以 MCP 服务方式接入（JSON-RPC over stdin/stdout）
python -m butian.cli mcp
```

### 接入 AI 应用

宿主应用支持 stdio MCP 时，配置命令 `python`、参数 `["-m", "butian.cli", "mcp"]`，工作目录设为仓库目录，环境变量 `BUTIAN_HOME` 指向你的数据目录。Python 应使用已安装本项目的解释器。不同客户端配置字段不同，请按宿主应用的 MCP 配置格式填写。

宿主 AI 自己负责理解目标和生成结果，调用补天的任务、上下文、证据、审核与记忆工具；这条路径无需 providers.json、模型 API Key 或 Ollama。补天主动启动独立子 Agent 时，才配置可选 Provider。没有 MCP/API/进程接口的应用只能人工交接。

### 控制台视图

总览、任务、验证、记忆、进化、成员六个工作区。「成员」视图展示成员身份与配置；随包初始资产会幂等导入；用户运行库不作为公共资产。其中「进化」是数字人自由进化的操作台：技能阶段、记忆合成、记忆维护（退化评估/降温/复温/版本链）、梦境自省（运行/蒸馏/抽象/提出假设/安排验证/记录结果）、验证批次、以及假设与验证队列。

## 数字人的初始知识与工具

安装后初始化十名数字人：许伟（嵌入式）、沈衡（仪器信号）、陆徵（系统架构）、宋析（数据分析）、苏衍（学习与验证）、何溪（交互设计）、陈墨（软件与测试）、林知（文献研究）、文澜（文档办公）、叶青（Web与可视化）。已有成员身份和用户记忆保留。

本次初始资产包含 **32 张专业方法卡、19 个工具资产和对应工具指南**。方法卡从本地有用技能及公开 TDD、Web 测试资料中提炼，按职责消化为判断步骤、适用条件、失败边界与核验方法。来源记录见 `butian/assets/catalog.json`；工具归属、依赖和输入契约见 `professional_tools.json`。

- 许伟：栈预算、工具链检查；沈衡：采样体检、不确定度、字符可检出性。
- 宋析：CSV 类型与结构审查；林知：文献记录规范化及 DOI 去重；文澜：PDF 页码、尺寸与文字层检查；叶青：HTML 静态结构审查。
- 每位数字人另有独立的基础复核工具，支持统计、独立不确定度分量合成、检查清单与文本指纹。
- 浏览器、Office 渲染和专有在线服务依赖宿主提供能力；初始资产不携带凭据，不将静态检查冒充实际操作验收。PDF 检查可选依赖 `pdfplumber`，图像分析可选依赖 OpenCV。

这些资产是 **未实践的方法知识**，不是已验证经验，也不是模型参数训练。知识保持 candidate、置信度为零，工具保持 draft；调用仍经过现有授权与执行后端。初始卡片不会自动作为新实践触发做梦。后续真实任务的结果才形成实践证据。

仓库随附 `butian/assets/initial_knowledge.sqlite3`，只包含公开数字人配置、知识和工具源码，不含用户运行数据库。可在新路径重建交换库，或创建可直接启动的干净运行库：

```bash
python -m butian.assets.build /absolute/new/initial.sqlite3
python -m butian.assets.export /absolute/new/runtime
```

目标必须不存在；命令拒绝覆盖已有目录或数据库。正常服务启动会从随包 JSON 和工具资源导入资产，重复启动不会重复登记。交换库不含运行期身份认证信息；运行库需在本机创建。
