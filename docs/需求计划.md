# 补天计划需求与实施计划

## 1. 项目定位

补天计划（Butian Plan）是一个与具体 AI 对话工具解耦的 AI 协作运行时。它允许用户配置数字人、岗位、职责和独立长期记忆，并通过子 Agent 执行具体工作。

项目不把“群聊里多个成员轮流发言”作为主要协作模型，而采用“一个派活者对接用户，多个子 Agent 执行任务”的结构：

```text
用户
  ↕
派活者 / 主 Agent：理解需求、拆解任务、分发、汇总、向用户交付
  ├─ 子 Agent：研究/分析
  ├─ 子 Agent：实现/操作
  ├─ 子 Agent：测试/验证
  └─ 子 Agent：审核/复盘
```

派活者是用户的直接对话人；子 Agent 是具有独立身份、岗位和记忆的组员。子 Agent 不应冒充用户，也不应绕过派活者直接改变最终交付结论。

## 2. 已确认需求

### 2.1 数字人资产

- 可以新增数字人。
- 支持把女娲计划（`nvwa_plan`）已有数字人资产迁移或导入补天计划。
- 导入时保留数字人的名称、人格设定、岗位、职责、模型配置和记忆资料。
- 迁移必须有明确的来源标识和版本信息，不能静默覆盖同名资产。
- 数字人资产与具体 AI 平台解耦，平台适配器只负责实际调用。

### 2.2 两种运行模式

补天计划必须支持运行时切换：

#### 单人模式

适合简单任务或用户希望直接与一个数字人工作时使用。

- 用户直接选择一个数字人。
- 该数字人负责理解、执行和回复任务。
- 仍使用该数字人的独立记忆、经验和教训。
- 不创建不必要的子 Agent，不产生虚假的团队协作记录。

#### 团队模式

适合复杂任务或需要分工、交叉验证和审核时使用。

- 用户只与派活者/主 Agent 对话。
- 派活者分析需求并创建任务树。
- 任务被分发给一个或多个子 Agent。
- 子 Agent 各自使用自己的角色提示、工具权限和独立记忆。
- 派活者收集结果并发起审核、返工或补充任务。
- 只有通过审核的结果才能进入最终交付。
- 用户可以查看任务状态、成员身份、执行证据和审核结论。
- 用户能否查看子 Agent 的原始对话，完全取决于接入的 AI 工具是否提供可点击打开的原生会话入口：工具支持则复用工具自身入口，工具不支持则不额外模拟或开发复杂查看功能。
- 用户在团队模式下不通过补天新增“停止”按钮；停止操作直接使用 AI 桌面工具原有的“终止对话/停止输出”按钮。Provider 必须感知终止并停止当前输出，记录 `cancelled_by_user`，不得把终止伪装成成功。
- 子 Agent 允许主动向用户提问。提问必须保留子 Agent 身份和任务上下文；若平台支持原生会话跳转则直接打开，若不支持则由派活者把问题转交用户，并将用户回答回填原任务。

模式切换要求：

- 当前模式必须在界面和 API 中明确显示。
- 切换模式不能丢失已有会话、任务或记忆。
- 切换只影响后续任务的编排方式，不篡改历史记录。
- 单人模式转团队模式时，当前单人数字人默认成为派活者；也允许在后台配置中指定固定派活者。未配置时使用当前开始对话的数字人。
- 派活者配置属于后台配置，不增加用户每次对话的选择负担；配置变更只影响新建会话，历史会话保留原派活者。
- 团队模式转单人模式时，正在运行的任务不得被静默取消。默认等待任务自然结束；只有用户通过 AI 工具原生终止输出，才记录为用户终止。

## 3. 核心角色模型

### 3.1 派活者 / 主 Agent

派活者选择规则：

- 后台配置项 `dispatcher_member_id` 可指定默认派活者。
- 未配置时，团队会话启动时的第一位派活角色数字人自动成为派活者。
- 派活者配置不等于用户身份，派活者的所有消息必须使用自己的数字人身份。
- 每个项目和会话保存实际使用的 `dispatcher_member_id` 快照，后续修改后台配置不得改变历史归属。

职责：

- 与用户进行唯一的主要需求对接。
- 将自然语言需求转为目标、约束、验收标准和任务树。
- 选择子 Agent，并为每个任务指定输入、输出、工具权限和截止条件。
- 追踪进度、处理阻塞、发起审核和安排返工。
- 汇总经过验证的结果，向用户说明证据、限制和未完成项。

派活者不得：

- 把尚未验证的子 Agent 输出直接包装成确定事实。
- 用用户身份发布子 Agent 的消息。
- 在没有执行证据时声称任务成功。

### 3.2 子 Agent / 组员

每个子 Agent 至少具有：

- `member_id`
- 名称和数字人资产引用
- 职级、岗位、主要职责
- 能力标签
- 可用模型或 Provider
- 工具权限范围
- 独立记忆库
- 当前任务和执行状态

子 Agent 的输出必须包含：

- 执行身份
- 任务 ID
- 使用的工具及版本
- 输入和关键假设
- 结果或失败原因
- 可复核证据
- 是否建议写入经验或教训

## 4. 任务与审核闭环

建议状态机：

```text
todo → ready → claimed → running → review → done
```

旁支状态：

```text
blocked / failed / cancelled
```

任务必须支持：

- 父子任务和任务树。
- 派活者分发和重新分配。
- 任务输入、输出、验收标准和证据附件。
- 超时、阻塞、失败、取消和孤儿任务回收。
- 审核通过、退回返工和返工次数上限。
- 任务 revision，防止旧结果覆盖新任务。
- 每次状态转换记录来源 Agent、时间和理由。

任务完成不是等于 Agent 返回文本，而是满足验收条件并拥有可追溯证据。

## 5. 上下文连续性与防黑洞

“上下文黑洞”定义为：信息曾经产生并可能仍在数据库中，但当前 Agent 因窗口限制、任务切换、会话重启、成员交接、摘要丢失或错误召回而看不到；或者 Agent 看到了结论，却不知道来源、版本、状态和下一步动作。

补天计划不得把上下文连续性寄托在 AI 工具自己的聊天窗口上。所有影响任务继续执行的信息必须写入结构化存储，并能在新会话中重建最小可用上下文。

### 5.1 当前任务状态包

每个运行中的会话和任务必须维护一个可重建的“当前状态包”，至少包含：

- 用户原始目标和最近一次明确修正。
- 当前模式、项目、派活者和成员身份。
- 任务树、当前任务、父任务、子任务和 revision。
- 已完成事项、未完成事项、阻塞原因和失败原因。
- 当前假设、约束、验收标准和禁止事项。
- 已采用的方法、已尝试的方法和不能重复的无效方法。
- 最近可靠证据及其路径、版本和来源。
- 待用户回答的问题和待外部工具返回的事项。
- 下一步唯一建议动作、负责人和触发条件。
- 当前上下文包的版本、生成时间和来源事件序号。

状态包不是普通摘要，不能只写成一段模糊自然语言。必须使用结构化字段，并保留原始事件引用。

### 5.2 上下文事件日志

所有会改变任务方向或记忆判断的事件必须追加写入不可变事件日志：

```text
user_goal
user_correction
constraint_added
constraint_removed
plan_created
task_created
task_assigned
progress_report
tool_started
tool_completed
tool_failed
agent_question
user_answer
evidence_added
memory_created
memory_reinforced
memory_disputed
memory_invalidated
review_requested
review_returned
provider_cancelled
session_compacted
session_resumed
```

事件至少包含 `event_id`、`session_id`、`task_id`、`member_id`、时间、顺序号、内容、来源、环境指纹和关联证据。事件只追加，不原地改写；错误应通过补充更正事件处理。

### 5.3 分层上下文模型

每次调用 Provider 时，运行时按层组装上下文，不把所有历史消息全部塞入窗口：

```text
L0 当前指令：本轮用户消息、当前工具结果、立即约束
L1 当前任务：任务状态包、验收标准、阻塞项、下一步动作
L2 近期事件：最近若干轮用户纠正、决策、失败和证据
L3 相关记忆：按环境、标签、任务类型和权重召回的经验/教训
L4 历史索引：更早事件的摘要、ID和可按需展开的原文位置
```

优先级必须是 `L0 > L1 > L2 > L3 > L4`。窗口不足时只能从低层开始裁剪，不能裁剪当前用户约束、当前任务状态、最近纠正、未决问题和下一步动作。

### 5.4 记忆召回契约

每次自动召回必须记录：

- `memory_id` 或 `tag_id`。
- `matched_by`：关键词、标签、环境、任务类型、相似度或关系链。
- `confidence` 和召回分数。
- 召回时的环境指纹。
- 是否为事实、经验、教训、推测或已争议内容。
- 为什么进入当前上下文，以及是否被实际使用。

`inferred`、`candidate`、`disputed` 内容默认只能作为低优先级参考，必须显式标记，不能无提示地混入确定性指令。`invalidated` 和环境不匹配的记忆不得进入默认上下文。

同一条记忆重复召回时应合并引用，不重复占用上下文窗口。召回结果必须有上限、总字符预算和按层预算，避免单条长记忆吞掉全部上下文。

### 5.5 长会话压缩与可恢复摘要

上下文接近 Provider 窗口上限时，必须先生成压缩快照，再开始新窗口。压缩不能只保留最近消息，必须保留：

- 用户目标和所有仍有效的纠正。
- 当前任务状态包。
- 已确认决策和被否决的决策。
- 可复用经验、教训、标签和环境版本。
- 证据索引和未完成事项。
- 原始事件范围、首尾序号和快照哈希。

压缩快照必须带 `snapshot_id`、`parent_snapshot_id`、`covered_event_from`、`covered_event_to`、生成模型、生成时间和校验哈希。原始消息和事件不得因压缩删除；摘要错误时可以从父快照和事件日志重建。

压缩后下一次调用必须明确携带“已从快照恢复”，并通过一致性校验确认当前任务 revision、成员、模式和最后事件序号没有倒退。

### 5.6 子 Agent 交接包

子 Agent 不能只返回一段聊天文本。每个任务交接必须生成结构化交接包：

```json
{
  "task_id": "task_xxx",
  "task_revision": 1,
  "member_id": "member_xxx",
  "status": "done|blocked|failed|needs_user",
  "summary": "结果摘要",
  "work_done": [],
  "work_not_done": [],
  "assumptions": [],
  "questions_for_user": [],
  "evidence_ids": [],
  "environment": {},
  "memories_created": [],
  "next_action": "下一步",
  "confidence": 0.0
}
```

派活者只读取当前 revision 的交接包。旧 revision 只能作为历史参考，不能覆盖新结果。交接包缺少状态、证据或下一步动作时，任务不能自动进入 `done`。

### 5.7 重启、断线和终止恢复

运行时重启后必须按以下顺序恢复：

1. 读取团队数据库中未终态会话和任务。
2. 校验最后事件序号、任务 revision、Provider 会话状态和锁。
3. 读取对应成员的当前状态包和最近快照。
4. 恢复未完成任务的输入、约束、证据、阻塞和下一步动作。
5. 能恢复外部会话则继续，否则明确标记 `provider_lost`，不得假装继续。
6. 对运行中但没有心跳的任务执行孤儿检测，超过阈值后进入 `blocked` 或 `failed`，保留原因。
7. 恢复后追加 `session_resumed` 事件，并向派活者明确说明恢复点。

用户终止输出只能终止当前 Provider 输出，不得删除已经产生的事件、证据或记忆。终止后必须记录终止位置，后续可以从任务状态继续处理。

## 6. 数据与运行时边界

补天计划分成三个必须可独立测试的层：

```text
core：成员、模式、任务、记忆、事件和状态机
runtime：SQLite、调度器、Provider 执行、日志和迁移
adapter：具体 AI 工具的会话创建、消息发送、终止和原生会话跳转
```

核心层不得直接读取桌面工具 UI，也不得假设所有平台都有群聊、子会话或原始对话查看能力。适配器必须声明能力：

```text
can_open_subagent_conversation
can_stream_output
can_cancel_output
can_receive_user_reply
can_create_child_session
```

能力为 `false` 时，核心只能使用替代流程，不能显示一个实际不可用的按钮或“已打开/已停止”的假成功。

## 7. 独立记忆系统

每个数字人拥有逻辑隔离的 SQLite 记忆空间。记忆系统不依赖具体 Harness 或模型的原生上下文记忆。

至少支持：

- 事实、偏好、经历、经验、教训、假设、关联、缺口和矛盾。
- 成员隔离、来源、重要度、置信度、验证状态、权重和归档。
- FTS 检索和按成员、类型、标签、时间过滤。
- 经验和教训专用查询，支持成员、类型、关键词、标签、环境版本、验证状态、权重、时间范围和归档状态筛选。
- 标签分为印象标签和抽象标签，两者都可查询、统计、衰减、合并和追溯来源。
- 记忆强化、降权、遗忘和归档。
- 整理：合并重复内容、标记过时内容、维护标签。
- 做梦：在经验和教训积累达到条件后，生成关联、缺口、矛盾和候选假设。
- 经验和教训自动吸收；人工确认不是学习前置条件。
- 客户异议、实际失败和新证据可以自动触发证伪、降权、修订或撤销。

### 7.1 印象标签与抽象标签

标签不是简单的字符串备注，而是可追溯、可衰减、可由实践更新的记忆索引。

#### 印象标签

印象标签记录 Agent 从具体实践中形成的局部判断，通常与一个成员、用户、项目、工具、任务类型或环境有关。例如：

```text
工具版本敏感
用户重视证据
该项目需要先真机验证
该方法容易产生假成功
某类任务适合先拆分再执行
```

印象标签要求：

- 必须关联来源记忆、任务事件或证据。
- 必须记录形成时间、最近验证时间、权重和置信度。
- 可以是正向、负向或中性印象。
- 不能把一次对话中的临时判断直接当成稳定事实。
- 新证据可以强化、削弱、修订或标记为争议。
- 过久未验证的印象必须按时间衰减，不能永久影响 Agent 行为。

#### 抽象标签

抽象标签是从多条经验、教训和实践事件中归纳出的较高层模式。例如：

```text
版本绑定
证据优先
防假绿
状态机闭环
用户身份隔离
平台适配
记忆污染风险
```

抽象标签要求：

- 至少由多条相关记忆或事件支持，不能只凭一条低置信内容生成。
- 必须保存支持它的记忆 ID、反例 ID和归纳时间。
- 必须区分“系统归纳”与“模型猜想”。
- 模型新归纳默认标记为 `inferred`，不能直接改变任务策略。
- 当支持记忆被证伪、过期或环境不匹配时，抽象标签要重新计算权重。
- 抽象标签可以关联多个成员，也可以限定到某个工具版本、项目或环境。

建议标签结构：

```json
{
  "tag_id": "tag_xxx",
  "kind": "impression",
  "name": "证据优先",
  "scope": {
    "member_id": "member_xxx",
    "project_id": "project_xxx",
    "tool": "工具名",
    "version": "版本号或 unknown"
  },
  "weight": 1.8,
  "confidence": 0.82,
  "origin": "observed",
  "support_memory_ids": ["mem_1", "mem_2"],
  "counter_evidence_ids": [],
  "last_verified_at": "时间",
  "status": "active"
}
```

`kind` 至少包括 `impression`、`abstract` 和 `candidate`；`origin` 至少包括 `observed`、`derived` 和 `inferred`。

标签更新规则：

- 相关任务成功并有证据：强化支持标签。
- 相关任务失败：强化失败标签或降低正向标签权重。
- 客户异议：只增加反证关联，不能直接删除标签或判定抽象结论错误。
- 反证评估为 `confirmed`：降低对应标签权重，必要时标记 `disputed` 或 `invalidated`。
- 反证评估为 `rejected`：保留标签，并补充原适用条件。
- 反证评估为 `inconclusive`：临时降低召回优先级，等待新证据。

### 7.2 经验与教训的版本绑定

使用外部软件、工具、模型、SDK、命令行程序或硬件时，经验和教训必须记录环境指纹，至少包括：

- 软件或工具名称。
- 版本号、构建号或 commit。
- Provider、模型名称和模型版本（可获得时）。
- 操作系统和架构。
- 关键配置、插件版本和依赖版本。
- 输入条件、复现步骤和观察结果。
- 证据路径、日志、命令输出或截图引用。
- 验证时间和验证者。
- 适用范围、失效条件和可信度。

同一条经验在不同版本环境下不得自动视为相同经验。版本无法确认时，必须标记为“版本未知”，不能伪装成精确结论。

建议结构：

```json
{
  "kind": "lesson",
  "title": "某工具在特定配置下的行为",
  "content": "可复现的经验或教训正文",
  "environment": {
    "tool": "工具名",
    "version": "版本号或 unknown",
    "provider": "服务名",
    "model": "模型名或 unknown",
    "os": "系统版本",
    "dependencies": []
  },
  "evidence": ["日志或产物路径"],
  "scope": "适用范围",
  "failure_conditions": ["失效条件"],
  "confidence": 0.0,
  "verification_status": "unverified",
  "reinforcement": {
    "success_count": 0,
    "failure_count": 0,
    "weight": 1.0,
    "curve": "log1p"
  },
  "status": "active",
  "tag_ids": ["tag_evidence_first", "tag_version_sensitive"],
  "lifecycle": "warm",
  "last_recalled_at": null,
  "recall_count": 0,
  "last_used_at": null,
  "useful_count": 0,
  "harmful_count": 0,
  "source_event_ids": []
}
```

### 7.3 记忆生命周期：热、温、冷和休眠

记忆不能只写入和累加，必须经历可解释的生命周期：

```text
candidate → warm → hot
              ↓      ↑
             cold ← 复用/验证
              ↓
           archived
```

- `candidate`：新产生但尚未充分验证的内容，默认低权重，只能作为候选参考。
- `warm`：已被实践验证或具有可靠证据，允许正常召回。
- `hot`：近期频繁使用且持续有效的记忆，优先进入当前任务上下文。
- `cold`：长时间未使用、近期未验证或权重下降的记忆，保留但默认不占用主上下文。
- `archived`：长期无效、重复、过时或已被替代的内容，保留索引和来源，默认不召回。

冷数据不是删除。一次新的相关任务命中冷记忆时，先以低置信参考方式复温；如果该方法在当前环境下再次成功，逐步恢复权重和生命周期等级。失败则保留冷态并增加反证或失效条件。

建议使用多因素生命周期分数：

```text
heat = evidence_quality × confidence × reinforcement
     × recency_decay × recall_utility
     × environment_match
```

状态迁移必须记录事件和原因，不能由一次简单的访问直接把记忆提升为热记忆。至少需要“被召回并实际使用”以及结果反馈；成功验证可升温，失败或有害使用可降温。

### 7.4 温故而知新：复温、重巩固和经验演化

为避免长期不用的经验彻底消失，同时避免过时经验污染新任务，增加以下机制：

- **冷记忆唤醒**：任务匹配到冷记忆时，以“历史经验，需重新验证”显示，不作为确定性指令。
- **复温窗口**：复温后的第一次使用单独记录结果，不直接继承旧权重。
- **重巩固**：相同环境下再次成功，更新最近验证时间、有效使用次数和权重；连续成功后再逐步从 `cold` 升至 `warm` 或 `hot`。
- **经验演化**：新实践不能只增加旧经验的计数。系统要比较新旧方法、结果、环境和证据，把更好的步骤、前置条件、工具选择、风险规避和验证方式合并为新的经验版本。
- **渐进改进**：同一经验多次实践后，可以形成 `v1 → v2 → v3` 的修订链。新版本只有在结果更好、证据更充分或适用范围更清晰时才提升为当前推荐版本。
- **版本复习**：工具或模型版本变化后，旧经验不直接失效，也不直接沿用；进入待复核状态，首次使用必须记录新版本结果。
- **主动复习**：整理或做梦时，可以从冷记忆中选择高价值、低风险的内容生成复习候选，但不能在无任务证据时自动宣布仍然有效。
- **间隔复习**：对高重要度且长期未验证的记忆安排低成本复核任务；复核失败则降权或建立修订版。
- **遗忘曲线**：长期未使用的召回分数按时间衰减，但保留原始内容、证据和来源，避免不可逆遗忘。

经验演化必须区分三种情况：

1. **强化**：方法没有实质变化，只是再次成功，增加支持次数和权重。
2. **优化**：目标相同但步骤、工具、配置或验证方式变得更好，创建新版本并记录改进差异。
3. **分叉**：同一方法在不同环境、版本或前置条件下表现不同，拆成条件分支，不能强行合并。

经验版本至少保存：

- `parent_memory_id` 和 `revision`。
- 本次新增或删除的步骤。
- 方法改进前后的差异。
- 新增证据和结果指标。
- 适用环境、前置条件和失效条件。
- 与旧版本相比的成功率、成本、耗时、质量或风险变化。
- 当前推荐版本及其推荐理由。

### 7.5 记忆质量、元认知与防污染

长期运行时，补天计划必须记录“记住了什么”以及“为什么相信它”，不能只保存结论。每条可影响任务行为的记忆应同时具有以下元数据：

- **来源等级**：原始观察、工具返回、测试结果、用户陈述、Agent 推断或做梦产物。
- **证据等级**：单次观察、重复复现、对照实验、独立来源交叉验证。
- **确定性状态**：`known`、`probable`、`uncertain`、`unknown`、`contradictory`。
- **适用范围**：适用项目、任务类型、工具、版本、输入和前置条件。
- **失效条件**：哪些变化会使结论不能直接使用。
- **新鲜度**：最近验证时间和时间衰减参数。
- **可用性反馈**：实际使用后的帮助、伤害、浪费步骤或导致返工情况。

#### “不知道”必须是一等记忆状态

以下情况必须明确产生未知或待验证状态，而不是让模型填空：

- 没有足够证据判断原因。
- 只有用户描述，没有复现或外部证据。
- 工具版本、输入或配置未知。
- 两条同等可信的记忆互相冲突。
- 只有做梦推测，没有实践验证。

当没有高可信记忆命中时，召回接口应返回 `unknown` 或 `no_verified_match`，并给出缺少哪些信息，而不是返回一条看起来合理但未经证实的答案。

#### 防止相关性冒充因果性

记录“方法成功”时必须区分：

- 方法确实导致结果成功。
- 方法与成功同时出现，但原因尚未确定。
- 只是观察到相关性。

没有对照、复现或因果证据时，记忆只能写成“可能相关”，不能写成“该方法必然导致成功”。做梦和抽象标签尤其不得把相关性自动升级为因果规则。

#### 偶然成功和幸存者偏差

一次成功不足以证明方法可靠。系统应记录尝试总数、成功数、失败数、取消数和未知结果，并在召回时展示样本量。被频繁尝试但只成功一次的方法不能仅因一次成功成为高权重经验；没有记录失败尝试的方法也不能获得虚假的高置信度。

#### 证据来源优先级

默认可信度排序建议为：

```text
可复现测试/工具真实返回
  > 多次相同环境实践
  > 单次带证据实践
  > 用户明确陈述
  > Agent 推断
  > 做梦候选
```

排序不是绝对真理；版本和适用范围不匹配时，高等级旧证据也不能直接覆盖当前环境的新证据。所有自动更新都必须保留原始来源。

#### 记忆更新的事务性和回滚

一次实践可能同时更新经验、标签、权重、冲突组和做梦触发计数。它们必须在同一事务或可恢复事件批次中提交，不能出现“权重已增加但证据没写入”的半成功状态。

发现错误学习后，系统应支持按事件批次回滚或反向修订：

- 撤销错误的强化事件。
- 重新计算受影响的权重和标签。
- 重新评估抽象标签和推荐版本。
- 保留回滚原因、执行者和时间。
- 不删除原始证据和错误历史。

#### 间隔复习和对照实验

对于高重要度、低证据或长期未验证的记忆，做梦或整理可以提出复习任务。复习任务必须明确：

- 复习目标。
- 当前记忆版本。
- 最小复现步骤。
- 成功和失败判据。
- 环境指纹。
- 是否需要与当前推荐版本做 A/B 对照。

复习任务的结果可以强化、优化、分叉或证伪原经验，但不能只因为“重新想了一遍”就更新权重。

当前记忆记录由新版本覆盖旧版本，召回和执行只使用当前版本；旧版本不再作为并列有效结论，但保留在版本历史中用于审计、回溯和比较。版本号只增不覆盖历史编号，不设置人为版本数量上限。新版本也不能仅因模型“觉得更好”就成为可信经验，必须由实际结果、可复核证据或明确的对照比较支持。

这实现的是完整的“温故而知新”：旧经验被重新唤醒，经过新实践验证后不断修订、优化和分化，最终形成更准确、更高效、更适合当前环境的方法，而不是永久冻结一条历史结论。

### 7.6 写入防污染与重复控制

记忆写入必须经过轻量规则闸门，防止每一轮聊天都生成垃圾记忆：

- 纯闲聊、未执行计划、无结果的猜测默认不写入长期经验或教训。
- 同一事件重复上报时使用事件指纹去重，不重复增加强化次数。
- 只有任务完成、工具返回、测试结果、用户明确反馈或可定位证据才能产生高权重实践事件。
- 单次成功只能产生一次成功强化；重试必须区分同一尝试和新尝试。
- 失败原因未确认时记录为“失败现象”，不能自动写成“根因”。
- 同一记忆的不同环境、版本和适用范围必须分支保存，不允许合并成一个无条件结论。
- 用户偏好、项目事实、工具行为和方法经验分开存储，避免一种记忆类型污染另一种类型。
- 自动写入必须保留 `source_event_ids`，找不到来源的记忆只能进入低置信候选池。

### 7.7 记忆冲突、竞争和版本分支

多个记忆对同一问题给出不同结论时，不得用最后写入者覆盖旧记忆。系统必须建立冲突组，并按以下维度比较：

- 环境和版本是否相同。
- 输入、配置和前置条件是否相同。
- 证据质量和可复现性。
- 最近验证时间。
- 成功/失败强化统计。
- 是否存在已确认反证。

如果只是适用范围不同，拆分为条件分支；如果在相同条件下冲突，保留 `contradiction` 关系并降低双方确定性召回分数，直到新证据解决。冲突本身可以进入做梦的知识缺口，但不能直接让模型自由选择一个结论。

### 7.8 召回后的使用反馈

记忆被召回不等于记忆有用。每次召回和使用应记录：

- 是否被 Agent 采纳。
- 是否实际影响任务决策。
- 使用后任务成功、失败、取消还是结果未知。
- 是否节省了步骤，是否导致错误或返工。
- 当前环境是否匹配。

只有实际使用并得到结果后，才更新 `useful_count`、`harmful_count` 和生命周期热度。对被多次召回但从未使用的记忆降低召回优先级，避免上下文黑洞和无效记忆占满窗口。

### 7.9 安全、隐私和删除边界

长期记忆不得自动保存密码、访问令牌、私钥、支付信息和其他不必要的敏感数据。敏感信息必须在写入前脱敏或拒绝写入。

用户要求删除时，系统应区分：

- 逻辑归档：从默认召回中移除，但保留审计记录。
- 彻底删除：按明确授权删除正文和索引，同时保留最小删除事件，不保留敏感原文。
- 纠错撤销：保留原记忆和证伪证据，标记为 `invalidated`，不伪装成从未存在。

记忆导出、迁移和恢复必须检查成员隔离，不能因相似标签或跨成员搜索把一个成员的私有记忆注入另一个成员。

## 8. 类人问题求解机制

人解决问题不是从记忆库取出一条答案直接执行，而是一个持续循环：

```text
理解问题
  → 明确目标和约束
  → 判断已知与未知
  → 调用相似经历和抽象方法
  → 生成多个候选解释/方案
  → 选择低成本、低风险的验证动作
  → 观察结果
  → 更新问题模型和方案
  → 形成可迁移经验或教训
```

补天计划的派活者和子 Agent 都必须遵循这个循环，不能把“检索到一条经验”当作问题已经解决。

### 7.1 问题表征和边界确认

每个新问题先建立问题模型：

- 用户想达到的目标和不想发生的结果。
- 输入、输出、约束、资源、截止时间和验收标准。
- 已知事实、未知信息、假设和争议点。
- 问题属于已知类型、相似类型还是全新类型。
- 哪些条件必须先向用户或外部工具确认。
- 什么结果可以证明问题已解决，什么结果只能说明部分进展。

问题模型必须独立于聊天原文保存，并在用户纠正时生成新 revision。问题没有定义清楚时，Agent 应提出最小必要问题或返回 `needs_clarification`，不能自行补全关键条件。

### 7.2 经验类比和迁移

遇到新问题时，系统可以召回相似经验、教训和抽象标签，但必须展示类比依据和差异：

- 相似的目标、结构、工具、约束或失败模式。
- 当前问题与历史问题的不同版本、输入、环境和风险。
- 哪些经验可以直接迁移。
- 哪些只能作为候选假设。
- 哪些历史条件不满足，不能迁移。

类比不是证明。历史经验与当前问题的环境匹配度不足时，只能进入假设池，不能作为确定性操作指令。

### 7.3 假设池和验证实验

硬件类假设必须进入独立的样机验证队列，状态为 `pending_prototype → prototype_received → batch_validating → validated/rejected/inconclusive`。在样机返回并完成预先登记的批量样本验证前，只能以低置信候选召回，不能升为 `warm` 或 `hot`，也不能作为确定性设计结论。批量记录必须保存样本数、通过数、失败数、测试条件和每个样本的证据引用；不完整、样本数不足或证据缺失时只能保持 `inconclusive`。

复杂或未知问题至少维护一个假设池，而不是只保留模型最先想到的解释：

```text
hypothesis_id
statement
支持证据
反对证据
前置条件
预测结果
验证动作
成本和风险
当前概率/置信度
状态：candidate|testing|supported|rejected|unknown
```

每个假设必须产生可观察预测。验证动作按以下原则选择：

- 优先低成本、可逆、信息增益高的动作。
- 先验证能区分多个假设的关键条件。
- 高风险、不可逆或会改变外部状态的动作必须先获得任务授权。
- 不能把“模型解释听起来合理”当作验证。
- 实验失败时区分假设被推翻、实验执行失败和结果未知。

验证结果要回写假设池、任务状态、证据和相关记忆。被拒绝的假设保留为失败经验，避免未来重复走同一条路。

### 7.4 探索与利用

Agent 需要在复用成熟经验和探索新方案之间平衡：

- 高置信、环境匹配的经验优先用于低风险路径。
- 新问题、冲突问题和旧方法失效时，保留探索候选。
- 探索预算必须可配置，不能无限试错。
- 探索产生的新方法先进入候选版本，经过结果比较后才成为推荐版本。
- 重要任务应保留至少一个替代方案或失败回退路径。

### 7.5 结果解释和复盘

问题完成后必须复盘：

- 真正解决了什么，哪些只是绕过或暂时缓解。
- 哪个假设被支持、拒绝或仍未知。
- 哪些步骤真正贡献了结果，哪些步骤只是同时发生。
- 使用了哪些工具、版本和外部知识。
- 是否产生新的经验、教训、抽象标签或待验证问题。
- 下次遇到同类问题应该保留、修改还是避免什么。

复盘结果必须关联任务、实验、证据和环境，不允许只保存一句“成功了”。

## 9. 外部知识学习：文章、论文到实践经验

网络文章和论文是外部知识来源，不是已经验证的本地经验。补天计划必须把外部学习拆成“来源、主张、适用性、假设、实践、验证”六层。

### 8.1 来源记录

每个外部来源至少记录：

- 标题、作者、发布者、URL、DOI 或其他稳定标识。
- 发布日期、访问日期、版本、修订号或 commit。
- 原文摘要、关键章节、引用位置和下载内容哈希。
- 来源类型：论文、官方文档、标准、项目文档、博客、论坛或用户经验。
- 可能的利益冲突、二手引用和来源可信度。

网页内容可能变化，必须保存访问时的快照或最小必要摘录，并保留原始链接。不能只保存模型生成的总结。

### 8.2 主张提取

Agent 先从文章或论文提取可核对的主张，而不是直接写成经验：

```text
claim_id
source_id
原文主张
证据位置
作者的前提和实验条件
数据和指标
限制条件
与已有记忆的关系
```

主张状态至少包括：`extracted`、`supported_by_source`、`disputed`、`not_applicable`、`tested_locally`。

论文中的实验结论只能说明作者实验条件下的结果，不能自动证明在当前项目、工具版本、硬件或模型上成立。

### 8.3 适用性分析

在把外部主张变成实践假设前，比较：

- 任务目标是否相同。
- 输入规模、数据分布和约束是否相同。
- 软件、硬件、模型和版本是否相同。
- 评价指标和成功判据是否相同。
- 文章中的基线、对照组和失败案例是否存在。
- 当前环境是否缺少关键前提。

适用性不足时，主张只能作为低置信候选，不得直接调整生产策略。

### 8.4 从主张生成实践假设

外部学习必须转成可验证假设：

```text
来源主张
  → 当前环境差异
  → 可检验假设
  → 最小实验
  → 结果和证据
  → 支持/拒绝/未知
  → 经验版本、教训或仅保留外部知识
```

例如论文声称某方法降低耗时，系统不能直接记录“该方法更快”，而应生成：当前工具和数据规模下，该方法预计降低多少耗时；随后设计对照实验，记录基线、配置、重复次数、波动、失败和成本。

### 8.5 学习结果分层

外部内容进入记忆时分层保存：

- `source_knowledge`：来源原文和主张，只表示“来源这样说”。
- `practice_hypothesis`：准备在当前环境验证的假设。
- `hardware_hypothesis`：涉及电路、器件、原理图、PCB、结构、热设计或实物接口的假设；即使来源是用户、模型、论文或历史经验，也只能作为待验证知识。
- `local_observation`：本地一次实践观察。
- `local_experience`：本地重复实践后形成的经验。
- `local_lesson`：本地失败后形成的教训。
- `generalized_pattern`：多个来源和本地实践支持的抽象模式。

只有 `local_experience`、`local_lesson` 和经过证据支持的 `generalized_pattern` 才能默认影响任务策略；来源知识和实践假设必须明确标记，不能伪装成本地验证结论。

### 8.6 外部学习的反污染规则

- 不把搜索结果摘要直接写入长期经验。
- 不把论文作者的结论改写成当前环境的事实。
- 不因多个网页互相转载就当作独立证据，必须追溯原始来源。
- 外部来源不能覆盖本地反复验证的相反结果；两者应形成冲突组。
- 引用内容与模型推断必须分开保存。
- 许可证、版权、隐私和访问权限必须遵守；只保存完成任务所需的最小内容。
- 来源失效、被撤稿、版本更新或出现勘误时，相关主张进入复核队列。

### 8.7 学习调度

学习任务可以由用户请求、任务缺口、做梦产生的知识缺口或周期性复习触发。调度器应区分：

- 先搜索已有本地记忆，避免重复学习。
- 再检索高可信外部来源。
- 提取主张和适用条件。
- 生成一个或多个实践假设。
- 安排低成本实验或在真实任务中观察。
- 根据结果更新记忆，不把未实践内容标记为成功经验。

## 10. 人类经验机制完整模型

补天计划的经验不能只是“成功/失败的一段文本”，而应模拟人解决问题时从经历到能力的完整链路：

```text
经历
  → 观察
  → 问题理解
  → 候选解释
  → 行动和验证
  → 结果
  → 复盘
  → 经验/教训
  → 方法和能力
  → 在新问题中迁移
```

### 9.1 经历 Episode

每次真实任务、实验、工具操作或用户反馈形成一个 `experience_episode`，至少记录：

- 参与成员、任务和项目。
- 时间、环境、软件/模型/硬件版本。
- 遇到的问题和目标。
- 输入、约束、资源和风险。
- 采取的行动和实际步骤。
- 观察到的信号、结果、代价和意外。
- 原始证据、日志、文件、测试和用户反馈。
- 哪些内容是事实，哪些内容是当时的解释。

一次经历不能直接等于通用经验。它首先是带证据的事件，后续通过复盘和多次实践归纳。

### 9.2 情境模型 Context

经验必须回答“在什么情况下有效”：

- 任务类型和目标。
- 工具、模型、硬件、版本和配置。
- 输入规模、数据分布和前置条件。
- 时间压力、可用资源和失败代价。
- 适用条件、禁用条件和失效信号。

召回时必须同时展示历史情境和当前情境的匹配项、差异项及差异风险。

### 9.3 解释模型 Explanation

经验要区分观察与原因：

```text
observed_fact       观察事实
interpretation      当前解释
causal_hypothesis   因果假设
validated_cause     已验证原因
unknown_cause       原因未知
```

“采取 A 后成功”不能自动写成“因为 A 所以成功”。一个经历可以保留多个候选原因、支持证据、反例和下一步验证。

### 9.4 方法模型 Procedure

成熟经验必须能够转化为可执行方法：

```json
{
  "trigger": "触发条件",
  "preconditions": [],
  "steps": [],
  "checkpoints": [],
  "success_criteria": [],
  "failure_signals": [],
  "fallback": [],
  "rollback": [],
  "cost": {},
  "risk": {},
  "expected_information_gain": 0.0
}
```

经验不只告诉 Agent“知道什么”，还要告诉它“下一步怎么做、观察什么、何时停止、失败如何回退”。

### 9.5 记忆类型和能力类型

至少区分：

- 陈述性记忆：知道事实、概念和工具行为。
- 程序性记忆：知道如何执行一组步骤。
- 条件性记忆：知道什么时候使用某方法。
- 禁止性记忆：知道什么时候不能使用某方法。
- 诊断性记忆：知道从现象到检查路径。
- 反事实记忆：知道不做、换工具或换环境可能发生什么。

当多条同类经验在相近情境下稳定有效时，可以沉淀为岗位能力或检查清单，但能力必须保留支持它的经历和失效边界。

### 9.6 显著性和优先级

人不会平均保存所有经历。记忆显著性由以下因素共同决定：

```text
novelty × surprise × cost × risk × impact × user_feedback × goal_relevance
```

高风险失败、重大突破、用户强烈纠正、异常结果和长期目标相关事件应提高保留和复盘优先级。低价值重复成功不能无限压过一次重要失败。

### 9.7 抽象思维与具体经历的双向检索

抽象标签和具体经历必须双向连接：

```text
具体经历 → 抽象模式/标签/能力
抽象模式/标签/能力 → 相关具体经历
```

当 Agent 只想到“这属于版本绑定问题”“这可能是假成功”“以前好像遇到过类似问题”时，系统必须允许从抽象节点反向展开：

- 相关经历列表。
- 最相似的原始问题和环境。
- 当时采取的步骤。
- 当时的结果、证据和失败边界。
- 当前问题与历史经历的共同点和差异。

抽象节点只能作为记忆索引，不能伪造一段不存在的回忆。若只能匹配到抽象标签而没有可靠具体经历，必须返回“抽象上相似，但没有可验证的历史经历”。

反向检索结果需要记录 `recall_path`，例如：

```text
abstract_tag → capability → memory_pattern → episode → evidence
```

抽象标签、能力和具体经历的权重独立计算，防止一个抽象标签被误强化后带动所有下属经历一起升权。

### 9.8 元认知和未知状态

每个经验都要回答：

- 我知道什么。
- 我可能知道什么。
- 我不知道什么。
- 我为什么这么认为。
- 下一步如何验证。

没有高可信经验命中时必须返回 `unknown` 或 `no_verified_match`，不能用相似文本填空。

### 9.9 反事实和迁移

重要经验可以生成反事实问题：

- 如果不执行这个步骤会怎样。
- 如果更换工具或版本是否仍然成立。
- 如果前置条件改变，哪一步会失效。
- 如果结果失败，是否存在替代原因。

反事实必须标记为推测，除非有实际对照实验支持。经验迁移到新问题时，必须记录迁移依据、差异、风险和验证结果。

### 9.10 经验模型示例

```text
experience_episode
├─ problem
├─ context
├─ actions
├─ observations
├─ result
├─ evidence
├─ explanations
├─ hypotheses
├─ procedure
├─ lessons
├─ counterfactuals
├─ revision_history
└─ capability_links
```

### 9.11 经验到能力的沉淀

能力不是标签的别名，而是可以在一类问题上稳定执行的方法集合。能力形成至少需要：

- 多个独立经历支持。
- 明确的触发条件和适用边界。
- 可执行步骤和验收标准。
- 多次成功与失败统计。
- 至少一个已知失效条件。
- 可回溯的经历、证据和版本。

能力召回后仍需根据当前情境验证，不能因为成员“擅长某事”就跳过检查。

## 11. 自动吸收、强化与证伪

经验和教训由实践结果自动吸收，不要求先经过人工确认：

- 做事成功：自动记录为经验，记录采用的方法、环境、工具版本、证据和适用条件。
- 做事失败：自动记录为教训，记录失败方法、错误现象、根因证据、环境和避免条件。
- 同类方法再次成功：增加成功次数和权重。
- 同类方法再次失败：增加失败次数，降低权重，并更新失效条件。
- 客户提出异议：把异议作为新的反证事件，自动关联到相关经验或教训，进入待评估状态；异议本身不等于证伪成立。
- 新版本、新配置或新工具行为与原结论不一致：覆盖当前记忆正文并生成递增版本；环境指纹不同则在新版本中标记适用范围或建立分支，历史版本仍保留审计。

强化权重使用对数增长曲线，建议使用 `log1p(n)` 或等价的饱和函数：

```text
reinforcement = base_weight + gain * log1p(success_count)
```

失败也使用对数曲线计算惩罚，避免一次偶然失败抹除长期有效经验，同时避免重复成功无限放大权重。达到一定次数后，新增一次成功的收益会自然降低。最终召回分数还应综合环境匹配度、最近验证时间、证据质量和当前状态。

经验和教训的状态至少包括：`active`、`disputed`、`superseded`、`invalidated`、`archived`。自动证伪不等于物理删除，必须保留原内容、反证事件、修订链和时间线。

### 11.1 反证事件评估

反证事件必须由系统依据证据判断，不能因为用户或客户说了“错了”就直接证伪。评估流程为：

```text
客户异议/失败现象
  → 记录反证事件
  → 核对任务输入、环境指纹、工具版本和原适用范围
  → 检查是否复现、是否存在替代解释
  → 交叉比对原证据与新证据
  → 判定 confirmed / rejected / inconclusive
  → 更新权重、适用范围和状态
```

判定规则：

- `confirmed`：在相同或明确匹配的环境、输入和配置下，新证据可复现地推翻原结论，或原结论的关键前提已被证明确实不成立。此时才允许将经验标记为 `invalidated`、建立修订版并显著降权。
- `rejected`：异议无法复现，或新证据表明问题来自不同版本、不同输入、错误操作、环境差异或其他原因。原经验保留，必要时补充适用范围。
- `inconclusive`：证据不足、版本未知、输入不完整或存在多个同样合理的解释。原经验暂不证伪，可标记 `disputed` 并降低召回优先级。

系统应优先尝试自动复现和证据比对；无法自动复现时必须保留不确定状态，不能猜测结论。客户异议可以立即降低临时召回权重以避免风险，但只有 `confirmed` 才能完成证伪。

### 11.2 经验与教训查询

经验和教训查询必须返回完整正文以及来源、环境指纹、标签、权重、验证状态和证据，不允许只返回标题或摘要。

建议接口：

```text
memory.search
memory.experiences
memory.lessons
memory.tags
memory.impressions
memory.abstracts
```

查询参数至少支持：

```text
member_id
kind=experience|lesson
q
tag
tag_kind=impression|abstract|candidate
status
verification_status
tool
version
project_id
min_weight
created_after
created_before
include_archived
limit
```

结果必须包含：

- 记忆或标签的完整正文。
- `memory_id` 或 `tag_id`。
- 成员、项目和任务来源。
- 工具、模型、系统和依赖版本。
- 印象标签、抽象标签及其权重。
- 支持证据和反证事件。
- 当前状态、置信度、验证状态和最近更新时间。
- `matched_by` 和 `confidence`，说明为什么命中以及命中可信度。

没有满足筛选条件时返回空结果，不猜测相似内容替代真实命中。

## 12. 做梦和自进化机制

做梦的主要触发条件是记忆积累，而不是固定时间到了就运行，但原有保护逻辑必须保留。系统应在同一数字人的经验和教训积累达到阈值，且存在足够的有效记忆事件时，才具备触发资格；随后仍必须同时通过时间间隔、锁和预算闸门。

默认闸门：

- 距离上次做梦达到最短间隔，避免连续重复消耗模型。
- 自上次做梦以来新增片段达到最小数量，默认可从 5 个起步并配置化。
- 做梦锁可获取，避免同一成员并发做梦。
- 单轮操作数、模型调用次数和成本不超过上限，默认可从 50 个操作起步。
- 没有足够有效材料、只有低置信推测或候选全部已证伪时，本轮跳过。

时间间隔不是唯一触发条件，记忆数量也不是无条件放行条件；四类条件共同防止做梦过早、过频或基于垃圾记忆展开。

做梦候选材料的选择遵循记忆强度和时间衰减：

- 从当前权重最高、证据最充分、最近验证过的记忆事件开始。
- 越久远、越少被验证、越少被召回的事件，进入梦境的概率越低。
- 权重低于召回阈值或已证伪的内容默认不进入梦境。
- 新近发生但尚未充分验证的事件可以作为低置信候选，但必须标记为推测。

建议使用带时间衰减的梦境采样分数：

```text
梦境分数 = 强化权重 × 环境匹配度 × 证据质量 × exp(-age / half_life)
```

做梦可以提出：

- 经验之间的新关联。
- 尚未解决的知识缺口。
- 互相冲突的经验。
- 可以在未来任务中验证的候选假设。
- 对任务拆解、工具选择和审核策略的改进建议。

做梦生成的内容默认属于 `inferred`，不能直接当作事实或正式教训。它可以进入候选池，并在后续实践中被验证、强化或证伪。这样既允许模型及时拓展想象，也不会让未经验证的联想污染长期记忆。

## 13. 女娲计划资产迁移

补天计划不从零开始。女娲计划中已经积累的数字人、岗位、任务经验、教训、工具踩坑和做梦产物，应作为初始资产导入。

迁移分为三类：

1. 数字人资产：名称、人格、职级、岗位、职责、能力和模型配置。
2. 结构化记忆：经验、教训、事实、标签、权重、验证状态和关联关系。
3. 证据与历史：原任务、日志、提交记录、测试结果、软件版本和来源路径。

迁移要求：

- 保留 `origin=nvwa_plan`、原始 ID、来源时间和迁移批次。
- 能读取到的工具版本、模型版本、系统版本和依赖版本全部写入环境指纹。
- 无法确认的版本写为 `unknown`，不补猜。
- 女娲计划中已经验证过的经验可以带入初始权重，但不能绕过版本匹配和适用范围检查。
- 做梦产物、低置信假设和未验证内容迁移后仍保持推测或未验证状态。
- 原数据库和原始文件只读保留，迁移失败可重试，不修改源资产。
- 同名数字人或同一经验冲突时建立迁移冲突记录，不静默覆盖。

第一批迁移来源至少包括女娲计划已有的成员人格、任务调度经验、群聊身份归因、历史滚动、经验教训查询、独立记忆、整理/遗忘/强化/做梦机制，以及实际工程中记录的软件版本和真机验证教训。

## 13.1 女娲计划已验证的软件闭环资产

以下不是重新设计的设想，而是女娲计划中已经实现或经过回归验证、值得直接吸收的闭环经验：

### 独立记忆闭环

- 使用 SQLite 保存成员隔离的长期记忆，并支持 WAL、FTS5 和归档。
- 记忆具有类型、来源、重要度、置信度、权重、验证状态和时间字段。
- 已有经验与教训查询接口，可按成员、类型、关键词、归档状态和数量筛选。
- 经验、教训不依赖 Harness 原生上下文，能够脱离原平台作为独立资产迁移。

### 维护与自进化闭环

- 已有整理、遗忘、强化和做梦维护轮。
- 做梦产出关联、缺口、矛盾和候选假设，推测内容保持 `inferred`，不能直接当成事实。
- 原有做梦闸门包含最短时间间隔、新增片段数和做梦锁；另有单轮操作数和模型预算限制。
- 后台维护任务有日志、运行状态和锁释放记录，不能只用“调用成功”作为完成证据。
- 维护异常、锁竞争和跳过原因必须进入日志，便于判断是条件未满足还是后台调度停止。

### 任务与协作闭环

- 任务状态机已经形成 `todo → ready → claimed → running → review → done` 主链，旁支包括 `blocked`、`failed` 和 `cancelled`。
- 任务支持自动推进、超时、孤儿回收、审核返工和退回次数上限。
- 审核入口放在当前用户会话附近，符合人在环的真实操作路径，不要求用户离开当前会话去找隐藏页面。
- 成员发言必须使用成员身份，不能把子 Agent 的进度冒充成用户发言。
- 结果必须区分执行者、任务、证据和最终汇总者，避免多成员协作时身份混淆。

### 群聊与界面交互闭环

- 群聊刷新采用“贴底跟随、翻历史保持”：用户在底部时新消息自动滚底；用户向上查看历史时，轮询不能强制跳回最新。
- 已有 `chat.read` 的序号读取和 `chat.markRead` 的按序号已读语义，可迁移为通用聊天协议。
- 会话内验收入口放在当前会话标题区域，同时保留完整团队管理页。
- 交互控件必须对应真实动作、真实数据和真实状态，不能只显示成功提示而没有后端结果。

### 工程验证与防假绿经验

- 修改源码后先构建，再用构建产物测试，避免测试实际运行旧代码。
- 关键流程必须有自动化守卫，不能只依赖手工点击验收。
- 全量回归曾达到 374 项、371 通过、2 跳过、0 失败；这类测试结果和提交记录应作为迁移证据保存，而不是只迁移代码。
- 任何“成功”都必须能由文件、数据库、日志、状态转换或外部工具真实返回值证明。
- 信息不足时宁可返回未确认或错误，不猜测一个看似权威的原因。

### 女娲计划的迁移边界

迁移可验证的规则、数据模型、测试和证据，不迁移任何单一 Agent 产品的插件界面、会话生命周期、内部事件或特殊功能。成员和任务数据中的 Provider 标识仅作来源元数据，不得改变核心状态机或记忆语义。

## 14. 通用 Agent Provider 接入抽象

核心层只依赖能力协商后的通用接口。Provider 可由任意 Agent 工具、模型 API、MCP 服务、本地进程或人工执行端实现；平台特有字段留在 Provider 实现内部，不进入核心数据模型。

```python
class AgentProvider(Protocol):
    provider_id: str
    def capabilities(self) -> ProviderCapabilities: ...
    def select_model(self, requested_model: str | None) -> ModelSelection: ...
    def create_child_session(self, member_id: str, prompt: str, model: str | None = None) -> ProviderResult: ...
    def cancel(self, provider_session_id: str) -> ProviderResult: ...
```

能力未声明或 Provider 无法确认时返回 `unknown`；明确不支持时返回 `unsupported`，不得推断成功。流式输出、用户回复、子 Agent 对话和取消均按能力逐项协商。Provider 会话记录仅作为通用执行适配的审计信封，不实现平台专属生命周期。没有可调用 API、MCP 或进程接口的工具只能由外部人工执行，不得宣称已自动调度。

## 15. 技术语言建议

第一阶段推荐 Python：

- 标准库能力足够强，适合 SQLite、HTTP、CLI、后台任务和数据迁移。
- 开发和调试成本低，便于快速迭代记忆与调度规则。
- `sqlite3`、`asyncio`、`http.server` 或轻量 Web 框架即可完成最小闭环。
- 对 OpenAI 兼容接口、Ollama、MCP 和本地脚本都有成熟生态。
- 不需要为了核心功能安装复杂运行时。

建议初始依赖保持很少：

- Python 3.11 或更高版本。
- SQLite（优先使用 Python 标准库 `sqlite3`）。
- `argparse`、`asyncio`、`sqlite3`、`pathlib`、`json` 等标准库。
- Web API 初期可使用标准库，确认接口稳定后再考虑 FastAPI。

需要注意：Python 本身仍需安装；“不安装太多环境”不能理解为完全零环境。可提供 Windows 启动脚本、版本检查和虚拟环境初始化脚本，减少用户手工配置。

## 17. 已确认的产品决策

以下决策已经确认，进入实现时不再作为开放问题：

1. 派活者采用后台可配置的 `dispatcher_member_id`。未配置时，默认使用本次团队会话开始时的派活角色数字人；实际使用的派活者写入会话快照。
2. 子 Agent 原始对话查看能力完全跟随 AI 工具能力。能点开就复用原生入口，不能点开就不额外开发复杂查看功能。
3. 团队模式不新增停止按钮。用户通过当前 Agent 工具的原生停止操作终止；仅当通用 Provider 声明支持取消时才发送取消请求，否则记录 `unsupported`，不得伪称已停止。
4. 子 Agent 可以主动向用户提问。支持原生跳转的平台直接跳转，不支持的平台由派活者转交并回填答案。
5. 女娲计划数字人的原 SQLite 历史记忆必须保留并迁移，源数据库只读留存，迁移过程可重试。
6. 记忆采用“每个成员独立数据库 + 团队编排数据库”方案：成员库隔离长期记忆，团队库保存成员、项目、会话、任务、事件和 Provider 运行记录。
7. 做梦默认开启，但仍必须通过记忆积累、时间间隔、新增片段、锁、预算和候选有效性等保护闸门。
8. 第一阶段采用 Python 3.11+，优先实现 CLI 和本地 HTTP API；不先做复杂 Web 控制台，也不先做大量平台 UI。平台适配器在核心闭环稳定后接入。

### 18.5 首个可运行闭环

第一阶段必须按以下顺序完成并测试：

1. `butian init` 创建配置、团队数据库和成员数据库。
2. 创建一个派活者和至少两个子 Agent。
3. 启动单人模式，用户消息由选定数字人直接处理。
4. 切换团队模式，当前派活角色成为派活者。
5. 派活者拆解一个父任务和两个子任务。
6. 子 Agent 各自执行并回传带身份、版本和证据的结果。
7. 派活者汇总，任务进入 `review`。
8. 审核通过进入 `done`，退回进入下一 revision。
9. 成功自动形成经验，失败自动形成教训。
10. 用户异议生成 `disputed` 反证事件，系统可返回 `confirmed`、`rejected` 或 `inconclusive`，不能直接删除旧记忆。
11. 积累足够记忆后，后台做梦通过全部闸门并产生 `inferred` 候选。
12. Provider 终止输出后任务和会话状态可追溯，绝不报告假成功。

### 18.6 问题求解与外部学习验收

- 新问题先形成目标、约束、已知、未知、验收标准和问题 revision。
- 相似经验召回时显示类比依据和当前环境差异，不能把类比当作证明。
- 复杂问题保留多个假设，每个假设有预测、验证动作和结果状态。
- 验证动作优先选择低成本、可逆且信息增益高的步骤；高风险动作不会被无授权执行。
- 被拒绝的假设保留为失败经验，后续不会被当作新答案重复推荐。
- 任务完成后有结果复盘，能够区分真正解决、暂时绕过、相关性和因果性。
- 网络文章或论文先保存来源和主张，再生成当前环境的实践假设。
- 外部来源的结论不会直接成为本地经验，必须经过本地实践或明确标记为未验证。
- 论文实验条件、版本、数据规模和评价指标会参与适用性判断。
- 文章或论文版本变化、撤稿、勘误或来源失效会触发相关主张复核。
- 外部学习会保留原文证据位置，区分来源内容与模型推断。

### 18.7 人类经验模型和学习机制验收

- 每次重要实践都能保存为经历，而不是只保存一句成功或失败摘要。
- 经历、观察、解释、因果假设、方法和教训能够区分。
- 经验能够生成触发条件、步骤、检查点、成功标准、失败信号和回退方案。
- 抽象标签、能力和具体经历支持双向检索；抽象相似但没有可靠经历时返回明确未知。
- 经验迁移会记录共同点、差异、风险和验证结果。
- 高显著性失败、重大突破和用户纠正不会被低价值重复成功淹没。
- 能力必须由多次独立经历支持，并保留失效边界。
- 反事实只作为假设，未经过对照实验不能当作事实。
- 新问题可以保留多个假设，并按信息增益选择验证动作。
- 经验学习不会因搜索到文章或论文就直接成为本地经验。

### 18.8 外部学习和实践验收

- 外部文章和论文保留来源、版本、证据位置和适用条件。
- 外部主张先进入 `source_knowledge`，再转为当前环境的 `practice_hypothesis`。
- 本地实验能区分支持、拒绝、结果未知和实验执行失败。
- 只有经过本地实践的主张才能成为默认可执行经验。

### 18.9 高级记忆机制验收

- 没有高可信命中时返回 `unknown` 或 `no_verified_match`，不会用猜测填空。
- 一次成功不会自动证明因果关系，相关性、因果性和未知原因能够区分。
- 记忆结果显示尝试总数、成功数、失败数、取消数和未知结果，避免偶然成功制造高置信度。
- 记忆来源等级和证据等级可追溯，做梦候选不会直接变成确定性规则。
- 经验、标签、冲突和做梦计数的更新具有事务性，不能产生半成功状态。
- 错误学习可以按事件批次回滚，并重新计算受影响的权重、标签和推荐版本。
- 高重要度、低证据或长期未验证的记忆能够生成带复现步骤和判据的复习任务。
- 长期未使用的记忆会按时间和使用反馈进入 `cold`，但原文、证据和来源仍可恢复。
- 冷记忆被新任务命中时以低置信历史参考注入，第一次使用必须等待新结果验证。
- 冷记忆在相同环境下再次成功后逐步升温，不能一次访问直接变成 `hot`。
- 同一经验的改进步骤会形成新的 revision，旧版本保留，新版本只有经过结果或证据比较才能成为推荐版本。
- 经验优化、单纯强化和环境分叉能够被区分，系统不会把版本变化误记成重复成功。
- 同一事件重复上报不会重复强化权重。
- 未执行的计划、无证据猜测和失败现象不会自动写成高置信经验或根因教训。
- 不同工具版本、模型版本或配置下的记忆不会无条件合并或召回。
- 被召回但未使用的记忆不会无限提升权重；有害使用会降低热度。
- 相同条件下的冲突记忆不会由最后写入者覆盖，必须保留冲突组。
- 经验、教训、用户偏好和工具事实不会因标签相似而跨类型污染。
- 记忆导出、迁移和召回遵守成员隔离。
- 敏感凭据不会写入长期记忆。

### 18.10 上下文连续性验收

- 长会话超过窗口后，用户目标、有效纠正、当前任务、约束、证据和下一步动作均能恢复。
- 压缩前后的任务状态、revision、成员和最后事件序号一致。
- 从压缩快照删除或损坏时，可以通过父快照和事件日志重建状态包。
- 低层历史被裁剪时，L0 当前指令和 L1 当前任务状态不会丢失。
- 子 Agent 交接包包含状态、证据、环境、未完成事项和下一步动作；缺字段不能自动完成任务。
- 同一记忆重复召回会合并，不会无限占用上下文预算。
- 已证伪、环境不匹配或低置信推测不会无提示地进入确定性上下文。
- 用户纠正会在后续调用和压缩恢复后继续有效。
- 重启后能恢复未终态任务；不能恢复 Provider 时明确报 `provider_lost`，不报告假成功。
- 用户终止输出后，已产生的事件和证据保留，任务状态可继续处理。

### 18.11 原有功能验收门槛

- 单人和团队模式切换不丢会话、任务和记忆。
- 子 Agent 消息永远不使用用户身份。
- 后台派活者配置对新会话生效，旧会话保持快照。
- 不支持打开子 Agent 会话的平台不显示假入口。
- 用户停止输出后不会继续写入新的模型输出，也不会将任务标记为完成。
- 女娲计划 SQLite 导入后成员、记忆数量、经验、教训和来源统计可核对。
- 同一环境下成功经验能够召回，不同版本环境不会无条件复用。
- 一次异议不会直接证伪；相同环境可复现的反证才能 `confirmed`。
- 做梦在任一闸门不满足时跳过并记录明确原因。
- 所有测试从源码构建或直接运行当前源码，禁止测试旧构建产物。
- 失败必须暴露真实错误和证据，不以“成功”或猜测原因代替。

本文件从此作为补天计划第一阶段的实现规格；后续变更必须追加决策记录并同步更新对应测试和验收门槛。

## 19. 开工前闭环审计与补充约束

本节是对前述机制的开工前审计结论。总体架构闭环，但以下边界必须作为第一阶段硬约束写入实现和测试；否则会出现记录存在但无法恢复、能力显示但实际不可用或实验结论不可复现的问题。

### 19.1 跨数据库一致性与事务边界

团队库和成员库是物理隔离的 SQLite 数据库，不能假设它们可以参加同一个原子事务。一次任务交接、记忆写入或状态转换必须采用“团队库事实 + 成员库事实 + 可重放事件”的提交协议：

1. 先生成全局唯一 `operation_id` 和幂等键，写入团队库操作记录，状态为 `prepared`。
2. 按固定顺序写入成员库和团队库的业务记录，每一步都带 `operation_id`。
3. 全部成功后将操作标记为 `committed`；任一步失败则标记为 `pending_recovery`，不得报告成功。
4. 重启恢复器按幂等键补偿、回滚逻辑状态或标记 `incomplete`，不能依靠人工猜测。

事件日志必须包含 `operation_id`、`aggregate_id`、`idempotency_key`、`event_schema_version` 和 `commit_state`。验收必须覆盖进程在每个提交阶段崩溃、重复请求、网络重试和成员库不可写。

### 19.2 并发、租约和幂等

任务领取、审核、取消、重试、做梦和迁移都可能并发，必须定义：

- 数据库写锁、任务租约 `lease_id`、持有者、过期时间和心跳。
- 同一任务同一 revision 只能有一个有效执行者；过期租约才能回收。
- 状态转换采用 `expected_revision` 条件更新，旧客户端提交必须返回 `revision_conflict`。
- 外部 Provider 请求、交接包、事件和记忆强化都必须支持幂等键。
- 取消与完成同时到达时按事件序号和 Provider 真实返回判定，不能按 UI 到达顺序猜测。

### 19.3 Provider 能力协商和模型配置

补天计划允许每个数字人保存 `provider_id`、`model_id`、参数和上下文限制，但这只是偏好，不代表任意桌面应用可以执行。会话启动前必须生成能力快照并进行协商：

- `requested_model`：成员偏好。
- `effective_model`：适配器实际采用的模型，或 `unknown`。
- `selection_status`：`applied|fallback|unsupported|unknown`。
- `fallback_reason`：平台不支持、权限不足、模型不可用或能力未知。

父会话和子会话都必须记录请求模型与实际模型。适配器不得把“调用了默认模型”伪装成“已使用成员模型”。没有 `can_create_child_session` 时，团队模式只能进入显式的串行/手动委派降级路径，并在交接包中标明。

### 19.4 用户提问、暂停和恢复回路

`needs_user` 不是终态。必须增加 `waiting_user` 任务状态和问题实体，至少包含 `question_id`、提问成员、问题上下文、选项或自由回答、截止时间、回答者和回填事件。用户回答只能回填原问题对应的任务 revision；过期或已取消问题必须拒绝写入并返回原因。

Provider 无法暂停时，子 Agent 提问前必须先结束或挂起当前调用，并保存可恢复输入；用户回答后新建续接调用。支持原生会话跳转的平台也必须同步写入补天事件，不能只依赖外部 UI 历史。

### 19.5 取消、超时与 Provider 丢失语义

取消请求只表示“请求停止”，直到适配器收到 Provider 的确认或确定超时前，任务状态为 `cancelling`。随后按真实结果进入 `cancelled`、`provider_lost` 或 `unknown`；不得因为本地按钮点击就断言模型已停止。超时同理，区分 `provider_timeout`、`transport_unknown` 和业务失败。

已产生的流式片段必须带序号和完整性标记；恢复时记录最后确认片段，重复片段按事件 ID 去重，缺口标记为未知，不能拼成看似完整的输出。

### 19.6 证据、文件引用与权限

证据不能只保存路径字符串。每条证据必须有类型、绝对/工作区相对路径、内容哈希、大小、产生时间、来源操作、访问权限和是否存在。文件变化后哈希不匹配必须显示 `stale`，不能继续作为当前证据。成员只能读取其被授权的证据；跨成员共享必须记录授权事件。

工具权限必须由任务授权快照冻结，不能因后台配置变化而在运行中扩大权限。不可逆操作要有显式授权事件和真实执行返回；模拟、计划和实际执行必须使用不同状态。

### 19.7 记忆安全和数据治理补充

敏感信息检测、脱敏和拒绝写入必须有可测试的规则，并记录“已拒绝写入”事件但不得把敏感原文写入日志。删除、导出、迁移和跨成员检索必须经过授权检查。成员库备份、快照和迁移副本同样属于长期数据，不能因为源库只读就绕过访问控制。

记忆写入不能只依赖模型输出的 `source_event_ids`；运行时必须验证事件确实存在、属于当前成员或被授权共享，且证据状态有效。验证失败的记忆只能进入隔离候选区。

### 19.8 外部学习和论文研究的可复现闭环

论文不是附带文档，而是补天计划的验证产物。项目必须新增 `docs/论文/`，至少包含研究问题、假设、实验协议、指标定义、数据字典、运行环境、结果和威胁分析。论文实验不得只比较“有记忆/无记忆”，至少设置：

- `B0`：无长期经验机制的基线。
- `B1`：只有检索记忆、无强化/证伪/版本演化。
- `B2`：完整补天机制。

每个条件使用相同模型能力、工具权限、任务集合、随机种子预算和最大调用预算；模型或 Provider 不可完全固定时，必须分层记录并在统计中作为因素。任务集合分为重复问题、新问题迁移、冲突证据、外部论文转实践和长会话恢复五类。

至少记录：首次解决率、重复问题解决率、迁移成功率、尝试次数、耗时、模型调用数、成本、失败复发率、上下文黑洞次数、无依据断言率、`unknown` 诚实率、抽象到具体经历召回率、外部主张转本地经验率、人工审核负担和取消/恢复成功率。上下文黑洞必须有操作性定义：要求恢复的信息已存在于事件/快照中，但当前 Agent 未召回或召回后无法正确使用；每次漏召回都记录证据。

每次实验必须保存任务包哈希、数据集版本、代码 commit、配置、模型/Provider 版本、环境指纹、原始事件日志、统计脚本和失败样本。报告均值、离散程度和置信区间；不得只报单次最好结果。论文结论必须限定在实验条件内，外部论文主张仍按来源知识、实践假设、本地观察、本地经验分层。

### 19.9 第一阶段开工阻断项

以下任一项未实现或无测试，第一阶段不得宣称“闭环完成”：

- 跨数据库操作协议和崩溃恢复。
- 任务 revision、租约、幂等和旧结果拒绝。
- Provider 能力快照、模型实际回报和降级标记。
- `waiting_user` 提问回路。
- `cancelling`、`provider_lost`、片段去重和未知结果。
- 证据哈希、权限和过期证据识别。
- 成员隔离、敏感信息防写入和删除/导出授权。
- B0/B1/B2 论文实验协议及上下文黑洞可计量指标。

审计结论：补天计划的产品机制已形成总体闭环，但在上述补充约束落地并通过故障测试前，只能称为“设计闭环”，不能称为“实现闭环”。

## 20. 团队协作反向学习：向成功成员提问

团队成员之间允许出现一种特殊学习事件：成员 A 的任务失败或未完成，而成员 B 在相同或相近任务上成功，A 可以询问 B 的做法。这个过程不是闲聊，也不能把 B 的回答直接当作可靠经验，必须经过以下闭环：

1. **触发条件**：系统发现任务结果存在对照差异，记录 asker、expert、任务、环境版本、工具版本、模型版本、输入约束、双方结果和证据引用。相关性不等于因果，不得直接写成“B 的方法导致成功”。
2. **协作提问**：生成 `peer_learning` 记录，至少包含 `learning_id`、提问成员、被询问成员、问题、任务 ID、对照情境、创建时间和状态。A 不得向自己提问冒充团队学习。
3. **成功成员回答**：B 可以提供步骤、配置、前置条件、失败规避和验证方式。回答必须保留原文，不得改写成确定结论。
4. **候选经验**：回答进入提问成员自己的独立记忆库，类型为 `peer_learning_candidate`，状态为 `candidate`，低权重、低置信度，并携带来源学习事件、回答成员和“需要复现”标记。它可以帮助形成验证计划，但不能直接作为确定性操作指令。
5. **本地复现**：派活者为 A 生成低风险验证任务，尽量固定版本、输入、工具和权限；验证时记录实际步骤、观察结果、失败结果和证据哈希。
6. **证据判定**：复现成功后候选经验才可升级为 `warm` 或更高状态；复现失败进入 `rejected` 或保留为带限制的候选；证据不足为 `inconclusive`，不得升温。
7. **差异归因**：验证记录必须区分“回答中的方法有效”“环境差异导致结果不同”“描述不完整”“偶然成功”和“原因未知”。只有实验支持时才生成因果解释。
8. **经验传播**：验证后的经验默认只写入 A 的成员库；需要共享给团队时，必须形成脱敏的团队候选模式并保留来源成员、证据和适用环境，不能复制私有上下文。

状态流转：

```text
asked → answered/candidate → verifying → verified
                                  ├→ rejected
                                  └→ inconclusive
```

验收要求：同一任务存在成功和失败成员时可以发起提问；回答不会直接提高经验置信度；无复现证据不能进入 `warm`；复现失败不会删除原回答；版本或输入不同必须显示差异并降低迁移置信度；完整过程可从事件和证据反查。


## 21. 人类思考逻辑到系统机制的补充映射

论文中的认识论必须落到运行时，新增以下硬约束：

- 经验必须保存问题表征、目标拆解、假设、预测、行动、观察、替代解释、反事实问题和验证结论。
- 召回经验时同时展示相似点、差异点、环境匹配度、版本、证据等级和反例，类比只能生成候选假设。
- 经验排序除成功率外，还要考虑信息增益、验证成本、风险、样本量、新鲜度和置信度校准。
- 失败必须分类为知识、执行、工具、环境、沟通、测量或随机失败，分类不确定时保留 `unknown`。
- 系统必须记录验证前预测与验证后结果，用于校准过度自信；不得使用模型自报置信度作为唯一证据。
- 高权重经验要主动进行反例测试；存在强反例时冻结自动传播并生成复核任务。
- 经验、知识、技能和教训分开存储；外部文章和成员回答默认不是本地经验。
- 停止任务时记录停止理由，不得把预算耗尽、接口断开或人工放弃报告为验证成功。
- 同一方法在不同版本、输入和环境下可能形成冲突分支；当前正文采用经证据选择的版本，历史分支保留在版本链中，不能粗暴平均或删除冲突证据。
- 高风险、不可逆操作需要更高证据等级和显式授权；低风险模拟优先用于信息获取。

“实践是检验真理的唯一标准”在本系统中对应的可执行规则是：主张可以来自模型、来源、类比、梦境或成员回答，但只有有边界、可追溯、可复现的实践证据才能升级其验证状态；一次成功不等于普遍真理，实践失败也必须先排查表征、条件、执行和测量错误。


## 22. 数学闭环修复后的硬规则

形式化状态图和数值审计发现的漏洞已转为以下不可绕过规则：

1. 任务状态转换必须调用统一状态机；数据库接口不得接受非法边。
2. 同一 `operation_key` 重复提交必须幂等返回，不能重复产生事件或改变 revision。
3. 经验验证必须写入唯一的 `memory_verifications`；重复上报同一操作不能重复强化。
4. 协作候选经验至少经过两次独立成功验证后才能进入 `warm`；一次成功只能保留 `candidate/supported_once` 语义。失败、未知和过期证据不能升温。
5. `warm/hot` 记忆必须具有来源事件；直接绕过验证的写入被拒绝。
6. 成员协作提问、回答和验证必须先写入团队事件，成员记忆引用真实 `event_id`，不能把业务 ID 冒充事件 ID。
7. 若参数命名为 `half_life`，衰减使用 `2^(-age/half_life)`；若使用 `exp(-age/tau)`，参数必须命名为 `tau`，两者不得混用。
8. 召回先做状态和安全准入，再做权重排序。候选、环境未知和冷记忆可以进入低置信候选区；`invalidated` 不得进入默认确定性上下文。
9. 权重强化必须封顶或归一化，并与置信度、证据等级、环境匹配和新鲜度分开计算，不能用单个乘法分数承担全部语义。


### 7.8 记忆整理梦与抽象梦运行时契约

梦境分为候选生成、记忆整理和模式抽象三个阶段。`DreamRunner.run()` 只产生带输入记忆 ID 的候选，不代表候选已经正确。

- 整理梦通过 `distill_memories()` 保存原始记忆 ID、压缩摘要、合并项、冲突项、丢弃项、信息损失比例和可逆标志。原始记忆不得删除或被摘要覆盖；摘要必须保持 `candidate` 状态，并且同一输入指纹重复执行必须幂等。
- 抽象梦通过 `abstract_memories()` 保存支持记忆、反例、适用条件、失效条件和抽象层级。抽象模式默认是 `candidate`，不得直接变成 `warm`/`hot` 经验，也不得直接改变任务策略。
- 整理结果和抽象结果必须能沿来源 ID 回溯；模型认为“重复”或“无关”的内容只能记录在审计字段，不能静默丢弃。
- `information_loss` 必须在 0 到 1 之间，且整理必须可逆。发现冲突时保留冲突记录，不能用多数表决伪装成事实。
- 后续验证动作可以引用整理或抽象记录；只有带有独立证据的验证结果，才能按现有经验/教训状态机升级、退化或否决。
