## 3. 三条轨迹（本档真正的产出）

### 3.1 误伤：不答错，但复用收益归零，且不会自愈

`false-disputed` 组的三条记忆内容**是对的**，只是 bootstrap 时被一条失败观察打成 `disputed`（模拟一次误判）。

- 宿主按预注册策略，对 `disputed` 一律读源，于是 4 轮 12 题**全读源、全对**——误伤不会让它答错；
- 复用收益直接归零：这 3 个实体在 4 轮里**一次经验都没用上**，12 次读源、12 次全文档解析；
- 关键读数：settle 每轮都对它们记了一次成功观察，累计成功次数从 **3 → 4 → 5 → 6**，状态**一次都没离开 `disputed`**。
  因为计数规则要求「成功 ≥ 2 **且失败 = 0**」才转 `warm`，那一次失败永远在窗口里。

所以"误伤"不是"答错"问题，是**成本问题加单向锁**：内容对，但系统宁可每次都读源，也永不恢复复用。要解开只有一条路——`butian_memory_revise` 带新证据改写（把计数窗口重置），这正是 3.2 用的通道。

### 3.2 修订：一次修订 + 两次独立成功 = 回到复用（本轮实测 3 轮）

`repair` 组的三条记忆在 bootstrap 时被写成**错值**（`calibration` offset +37、`schema` divisor +7、`tool` factor +7），
但带两条独立成功观察，状态是 `warm`——正是 v2 里"上一批会话把提取错误写进经验库"的形态。

| 时刻 | 记忆状态 | 宿主行为 | 结果 |
| --- | --- | --- | --- |
| R1 recall | `warm` | 直接用经验 | **错**（三题全错，证明坏经验确实会被用上） |
| R1 settle | `warm` → `disputed` → `candidate` | harness 记失败，再用**新测量证据**执行 `revise` | 内容换成真值，计数窗口从修订时刻重算 |
| R2 recall | `candidate` | 按策略读源 | 对（第 1 次成功） |
| R3 recall | `candidate`（1 次成功） | 读源 | 对 → settle 时第 2 次成功 → **`warm`** |
| R4 recall | `warm` | 不读源，直接复用 | **对** |

修复通道是真的通了：`disputed` 的坏记忆在 3 轮里回到可复用，且 R4 起复用不再需要读源。
代价写清楚：**一次内容修订 + 两次独立成功观察 + 中间两轮仍要读源**，不是"改完立刻可信"。

### 3.3 规模：300 条同族无关记忆没有挤进任何一次召回

库内除 9 条任务记忆外，另预置了 300 条同族无关记忆（`calibration500..599` / `schema500..599` / `tool500..599`，状态 `warm`，内容是各自实体的 RULE）。

- 12 次召回（`scale` 组 3 实体 × 4 轮）**每次只返回 1 条**，就是提问实体自己那一版；无关条数合计 **0**；
- v2 时同一口径是"每次 45 条、无关 3060 条"（v2 结果 §11.1），本轮的规模压力下没有退化；
- 宿主 4 轮全对且 4 轮都没读源——规模既没污染答案，也没逼宿主去读源。

一处必须写下的边界：**查询的实体在库里没有记忆时不走闸门**。试点（`-pilot1`，未计入结论）里 `scale` 组最初没有预置记忆，
三次召回都退回或链兜底，各端回 **100 条**同族无关记忆——这是召回"宁可多给一条也不装作没经验"的有意行为（v2 §11.1 边界 1），
不是回归；正式数据因此把 `scale` 组改成有一条 `warm` 记忆。

## 4. 机制读数

1. **误伤与坏内容是两种病，代价不同**：坏内容会答错（v2 读数），误伤不会答错但把复用收益整块吃掉，而且**不能自愈**（6 次成功顶不掉 1 次失败）。
2. **`disputed` 的语义是"必须复核"，不是"低置信但仍可用"**：宿主 12/12 次读源，说明这条策略在真实模型上是稳定执行的，不是运气。
3. **修订的价值在"重置计数窗口"**：`revise` 之前，同一实体攒到 6 次成功也回不到 `warm`；`revise` 之后，2 次成功就够。差别不在证据多少，在窗口起点。
4. **恢复有明确节律**：`candidate` 期间宿主仍读源（不冒险），两次独立成功后才回到复用——这是"先保正确、再省成本"的排序，与预注册策略一致。
5. **规模不再是问题（到 300 条）**：IDF 闸门把"每次 45 条"压到"每次 1 条"，且实体存在时从不退回或链。

## 5. 有效性威胁与不能做的读法

1. **宿主是实验设计者，非盲**。本轮更重：宿主知道三组的构造，也可能"照着预期走"。缓解手段是判据看的是**记忆状态与读源行为**，不是宿主自述，但这条威胁不能消除。
2. **单宿主、单次运行**，不外推到其他模型，不报告 p 值；三组各 3 个实体，只做行为描述。
3. **记忆状态是 harness 直接注入的**（误伤、坏值、300 条无关记忆），不是真实历史事故；真实事故的分布未知。
4. **恢复节律依赖计数规则**（`successes >= 2 且 failures = 0 → warm`）。它是被测系统的一条设计，不是普适常数；换规则这段曲线的形状会变。
5. **"误伤组 4 轮都读源"不能读成"宿主不相信 disputed 记忆的内容"**：它只是执行了预注册策略；本轮没有测"如果不读源会不会答错"。
6. **`scale` 只到 300 条**，且召回仍是子串匹配 + IDF 闸门，没有向量检索或实体索引；千条以上不外推。
7. **不能读成"修订一定安全"**：本轮只测了"新证据正确"这一侧；证据本身错时 `revise` 会把坏值写得更硬，未测。
8. **不测量 token 成本与延迟**，所以"复用收益"只用"是否读源"这个二值代理，不给 ms 或 token 数。

## 6. 与 v2 的关系

| v2 第 9 节 | 本轮结论 |
| --- | --- |
| 第 1 条（误伤会不会过度读源、复用归零） | **回答**：会归零，且不会答错，也不自愈（3.1） |
| 第 2 条（修好坏记忆的正确路径） | **回答**：`butian_memory_revise` 这条路走得通，代价是 1 次修订 + 2 次独立成功 + 中间两轮读源（3.2）；"另立 memory_id"与"做梦通道重写"仍未比较 |
| 第 5 条（几百条记忆时是否顶得住） | **回答（到 300 条）**：召回 1.0 条/次、无关 0 条、宿主全对（3.3） |
| 第 3 条（跨模型是否同样执行"`disputed` 就改读源"） | 仍未回答——需要换模型再跑同一协议 |
| 第 4 条（每轮都漂移时会不会偷懒复用旧版本） | 仍未回答——本轮所有实体同版本 |

v2 与 v3 的关系是**修复前/修复后**：v2 记的是"坏经验把这条记忆永久钉死"的行为，v3 记的是补上内容通道之后行为怎么变。v2 的读数不改写。

## 7. 复现

```bash
PY="python"   # 或本机 python 3.12
OUT="docs/论文/experiment_results/host-loop-v3-20261102"
$PY "docs/论文/run_host_v3_multiround_study.py" --out "$OUT" --stage bootstrap
for N in 1 2 3 4; do
  $PY "docs/论文/run_host_v3_multiround_study.py" --out "$OUT" --stage recall  --round $N   # 宿主写 stages/rN-recall-decision.json
  $PY "docs/论文/run_host_v3_multiround_study.py" --out "$OUT" --stage source  --round $N
  $PY "docs/论文/run_host_v3_multiround_study.py" --out "$OUT" --stage settle  --round $N   # 宿主先写 stages/rN-answers.json
done
$PY "docs/论文/run_host_v3_multiround_study.py" --out "$OUT" --stage report
```

宿主侧的三份输入/输出（`rN-recall-decision.json`、`rN-answers.json`）在 `stages/` 里逐轮留档，可逐题复核。
`--stub` 只做管道自检，结果标 `host_kind = stub`，不得作为宿主结果引用。
